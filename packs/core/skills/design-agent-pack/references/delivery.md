# Доставка и совместимость пака

## Файловые скиллы и отдельно подключённый MCP

Используй этот вариант, когда целевые хосты уже загружают скиллы с диска или получают их из репозитория. Укажи способ установки скилла, способ подключения MCP-сервера, поддерживаемый транспорт и настройку доступа для каждого хоста. Хост обнаруживает скилл по его метаданным, а MCP-инструменты — через подключённый сервер. Проверяй оба пути независимо.

## Пак в multi-agent-kit

Храни исходники в `packs/<pack>/` выбранного источника. Если подходящий пак уже есть, добавь артефакты туда. Для проектной конфигурации используй установленный в репозитории локальный слой, если изменения нужны только этому проекту.

```text
packs/<pack>/
  pack.json                        # необязательное описание и значения vars по умолчанию
  skills/<skill>/SKILL.md
  skills/<skill>/references/       # материалы, которые читает скилл
  mcp/<integration>.json           # объект с ключом mcpServers, если пак задаёт подключение
```

`mcp/<integration>.json` описывает подключение к уже существующему серверу. Реализацию сервера, если она нужна, собирай и распространяй средствами её проекта. Проверяй, какие настройки подключения генератор переносит в каждый целевой хост. Для параметров окружения используй механизм `vars` с нейтральными значениями по умолчанию для несекретных данных. Секреты передавай через настройки авторизации или окружение, которые действительно поддерживает целевой хост.

Для проверки исходного пака запусти `lint` через CLI репозитория. Подключи исходник в тестовом проекте, выполни `sync` и `check`. Смотри сгенерированные пути и конфигурацию в проекте, а исправления вноси в исходный слой. Для текущего формата сверяйся с `docs/pack-format.md` в исходном репозитории multi-agent-kit.

## Skills over MCP

Выбирай этот вариант, если скиллы требуется обнаруживать и загружать с сервера. Для каждого целевого хоста проверь версию, поддержку расширения `io.modelcontextprotocol/skills` и совместимую ревизию MCP. Наличие обычных MCP Tools или Resources само по себе не подтверждает поддержку скиллов. Для хоста без расширения предусмотренный файловый вариант можно тестировать с тем же сервером инструментов. [Матрица поддержки расширений MCP](https://modelcontextprotocol.io/extensions/client-matrix).

При реализации сверяйся с действующей спецификацией расширения. Сервер объявляет расширение и поддержку Resources. Клиент обнаруживает скиллы через `skills/list`, получает сведения и перечень файлов отдельного скилла через `skills/get` и читает `SKILL.md` и нужные файлы через `resources/read`. Обычно файлы адресуются через `skill://`. Хост выбирает скилл по метаданным, загружает файлы по мере необходимости и применяет свои правила доверия и активации. Проверь, что инструкции загружаются с ожидаемого сервера и что чтение скилла само по себе не расширяет права. [Спецификация расширения Skills](https://github.com/modelcontextprotocol/ext-skills/blob/main/specification/beta/skills.mdx), [SEP-2640](https://modelcontextprotocol.io/seps/2640-skills-extension).

## Если пак будут устанавливать другие

Зафиксируй в формате распространения поддерживаемые хосты и версии, версии скиллов и зависимых серверов, требуемые права и порядок обновления. Свяжи версию скилла с диапазоном версий контракта инструмента, если они выпускаются отдельно. Для реестра или маркетплейса дополнительно определи идентификатор и происхождение пака, правила выдачи доступа и способ отката. Схему манифеста определяет система доставки. Для собственного загрузчика её можно определить самостоятельно, в том числе в `pack.yaml`.
