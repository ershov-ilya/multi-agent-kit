# Secure by Design — безопасность при создании цифровых сервисов

Источники: OWASP Top 10:2025, OWASP API Security Top 10:2023, OWASP Top 10 for LLM Applications:2025, OWASP Top 10 for Agentic Applications:2026, OWASP ASVS 5.0, OWASP Cheat Sheet Series, OWASP SAMM 2, CWE Top 25:2025 (MITRE/CISA), NIST SP 800-63-4 (июль 2025), NIST SP 800-207 (Zero Trust), NIST SP 800-61r3 (инциденты), NIST SSDF (SP 800-218), SLSA, CISA Secure by Design, классика Saltzer & Schroeder (1975), книги «Threat Modeling» (Shostack), «Security Engineering» (Anderson), «Alice and Bob Learn Application Security» (Janca). Там, где источники расходятся, в файлах отмечен канонический вариант.

## Суть подхода в восьми тезисах

1. **Безопасность — свойство дизайна, а не слой сверху.** Половина инцидентов (A06 Insecure Design, A01 Broken Access Control) не чинится патчем: ошибка в том, кому что разрешено и где принимается решение. Вопрос «что может пойти не так» задаётся на этапе RFC, когда менять дёшево.
2. **Весь ввод враждебен, пока не доказано обратное.** Запрос, заголовок, файл, вебхук, ответ чужого API, содержимое БД, вывод LLM. Данные и код разделяются механизмом (параметризация, кодирование под контекст), а не фильтром по чёрному списку.
3. **Deny by default и полная медиация.** Каждый запрос к каждому объекту проверяется сервером на «кто», «что», «с каким объектом». Клиент ничего не решает. Отсутствие проверки — уязвимость, даже если «так никто не сделает».
4. **Наименьшие привилегии везде.** Процесс, роль БД, токен CI, ключ API, агент LLM, сотрудник. Привилегия выдаётся на задачу и срок, а не «на всякий случай».
5. **Эшелонированная оборона.** Один контроль откажет. Параметризация плюс роль БД без DDL плюс RLS плюс лимит плюс алерт. Каждый слой самостоятельно ловит класс ошибок соседнего.
6. **Fail closed, но без DoS самого себя.** Исключение, таймаут, недоступность зависимости не должны открывать доступ (A10:2025). При этом отказ должен быть ограничен и наблюдаем.
7. **Криптографию не изобретают.** Выбирают проверенные примитивы, библиотеки и режимы, управляют ключами и ротацией. Самодельный шифр и «свой» хеш пароля — всегда ошибка.
8. **Безопасность измерима и проверяема.** Угроза записывается с вероятностью и ущербом, контроль — с тестом, который падает при его исчезновении. Что не покрыто тестом, со временем исчезнет при рефакторинге.

## Алгоритм работы агента

Полная версия с шаблонами и примером — в `references/playbook.md`.

1. **Определи режим**: брейншторм/RFC новой фичи, дизайн-ревью, код-ревью, аудит существующего, инцидент, короткий вопрос. Гибрид — норма. Если неясно, спроси: «проектируем новое или проверяем существующее?»
2. **Собери контекст**: что за актив (данные, деньги, доступ, репутация), кто пользователи и кто противник (скучающий пользователь, конкурент, бот-ферма, инсайдер, государство), границы доверия (клиент, API, ядро, БД, внешние сервисы), стек, регуляторика (ПДн, дети, деньги). Чего нет — запроси или зафиксируй допущение явно.
3. **Нарисуй поток данных и границы доверия** для фичи: откуда входит, где решается, где хранится, куда уходит. Каждая стрелка через границу — точка проверки.
4. **Пройди STRIDE по каждой границе** (подмена, подделка, отрицание, утечка, отказ, эскалация). Для ПДн добавь LINDDUN. Запиши угрозы в строку: «кто → что делает → с чем → последствие».
5. **Пройди по доменам карты**: для ведущих доменов фичи (обычно 3–5) открой файл домена и пройди его «Вопросы для брейншторма». Остальные домены пройди по таблице выше: одна строка «угроза или почему не применимо».
6. **Оцени риск**: вероятность × ущерб (или CVSS 4.0, если про конкретную уязвимость). Отсортируй. Выдели «нельзя выпускать без этого» и «после пилота».
7. **Назначь контроли** с эшелонами: предотвратить, ограничить, обнаружить, восстановить. Каждому контролю — тест или проверка, которая падает при его исчезновении, и владелец.
8. **Проверь принципы**: deny by default, least privilege, fail closed, минимизация данных, нет самодельной криптографии, решение на сервере. Нарушение любого — красный флаг для RFC.
9. **Выдай результат** в формате ниже: сводка, модель угроз, контроли, остаточные риски, что проверить тестами, что в чеклист релиза.

## Правила, выведенные из практики

- **Решение «можно ли» принимает сервер, и ровно в одном месте.** Клиент показывает, ядро решает. Дубликаты логики доступа расходятся и дают дыру.
- **Проверяй объект, а не только роль.** «Пользователь залогинен» и «пользователь — участник» не равно «этот оффер принадлежит ему». BOLA — первая уязвимость API пятый год подряд.
- **Параметризуй, а не экранируй.** Экранирование ломается при смене контекста. Параметризованный запрос, кодирование под контекст вывода, allow-list для всего, что уходит в интерпретатор.
- **Короткие секреты живут коротко.** Код входа: 6+ цифр, 5–10 минут, 3–5 попыток, одноразовость, привязка к каналу. Иначе перебор за минуты.
- **Не раскрывай существование.** Ответ на вход, восстановление и регистрацию одинаков по тексту, коду и времени, есть аккаунт или нет.
- **Один ключ — одна задача.** Ключ подписи не шифрует, ключ прод не живёт в dev, ключ CI не читает бэкапы.
- **Логируй событие, а не данные.** «Вход не удался для user_id» — да; код, пароль, токен, тело запроса с ПДн — никогда.
- **Зависимость — чужой код в вашем процессе.** Lock-файл, запрет скриптов установки, SCA в CI, пиннинг экшенов по SHA.
- **Ошибка — тоже ответ.** Единый формат, без стеков наружу, без разницы между «нет объекта» и «нет доступа», с correlation id для поддержки.
- **Для LLM: данные модели — не команды модели.** Чужой текст в промпте читается как данные. Инструменты с побочным эффектом — за подтверждением человека.
- **Каждому контролю — тест.** Тест на авторизацию («чужой не видит») обязателен для каждого эндпоинта с объектом.
- **Безопасность пропорциональна активу.** Для пилота на одном хосте хватит ASVS Level 1 плюс критичные пункты Level 2 для входа и доступа. Не требуй HSM там, где достаточно `age` и прав файла.

## Анти-паттерны

- Фильтровать «плохие символы» вместо параметризации и кодирования под контекст.
- Проверять права на фронтенде или только на списке, но не на объекте.
- Один админ-токен на всё; «временные» бэкдоры для отладки в проде.
- Самодельный хеш пароля, самодельный шифр, самодельный генератор токенов на `Math.random`.
- JWT без проверки `alg`, с секретом в репозитории, без срока и отзыва.
- Бесконечные коды входа без лимита попыток и без привязки к получателю.
- Секреты в `.env` в git, в логах, в URL, в сообщениях об ошибках.
- Бэкап без шифрования и без проверки восстановления.
- Зависимость «по звёздочке», экшены CI «по тегу», `curl | sh` в Dockerfile.
- Логировать всё тело запроса; не логировать события безопасности.
- Fail open: «если сервис проверки недоступен, пропускаем».
- Доверять выводу LLM как коду, SQL или командам; давать агенту инструменты «с запасом».
- Оправдывать отсутствие контроля тем, что «никто не догадается» (security by obscurity).
- Считать пентест раз в год заменой тестам и SCA в каждом билде.
