# D4. Авторизация и изоляция

> Аутентификация ответила «кто». Авторизация отвечает «что ему можно с этим объектом». Broken Access Control — первая категория OWASP с 2021 года, BOLA — первая в API Top 10 с 2019. Причина проста: проверка роли есть, проверки объекта нет.

OWASP A01:2025 Broken Access Control; API1:2023 BOLA, API3:2023 BOPLA, API5:2023 BFLA; CWE-862 Missing Authorization (#4 в Top 25:2025), CWE-863 Incorrect Authorization, CWE-639 Authorization Bypass Through User-Controlled Key (#24), CWE-284 Improper Access Control (#19), CWE-269 Privilege Management. ASVS 5.0: V8 Authorization.

## Три уровня проверки

| Уровень | Вопрос | Уязвимость | Пример |
|---|---|---|---|
| **Функция** (BFLA) | Может ли эта роль вызывать этот метод? | Обычный пользователь вызывает `/admin/users` или `DELETE` вместо `GET` | Модератор-эндпоинт без проверки роли |
| **Объект** (BOLA/IDOR) | Может ли этот субъект работать с этим конкретным объектом? | `/offers/123` → `/offers/124` чужой | Оффер другого пользователя или другого сообщества |
| **Свойство** (BOPLA) | Какие поля объекта субъект может читать и писать? | Ответ отдаёт `phone` до согласия; запрос пишет `status=accepted` | Контакт в JSON «на всякий случай», mass assignment |

Все три проверяются сервером при каждом запросе. Проверка на списке (`GET /offers` фильтрует по пользователю) не заменяет проверку на объекте (`GET /offers/:id`).

## Модели доступа

| Модель | Суть | Подходит | Ограничение |
|---|---|---|---|
| **RBAC** | Роль → набор разрешений | Админ/модератор/участник | Не знает про объекты: «участник» не значит «владелец этого» |
| **ABAC** | Правило над атрибутами субъекта, объекта, среды | «Участник того же сообщества, статус active, время рабочее» | Сложность отладки; нужен движок политик |
| **ReBAC** | Отношения: `user —member→ community —owns→ offer` | Многоарендность, иерархии, шаринг (Zanzibar, OpenFGA, SpiceDB) | Инфраструктура; для пилота избыточна |
| **ACL на объекте** | Список субъектов с правами на объекте | Документы, файлы | Не масштабируется на группы без ReBAC |
| **Capability / scoped token** | Токен сам несёт право на объект | Ссылки-приглашения, временный доступ к файлу | Отзыв и утечка токена |

Практика для продукта среднего размера: RBAC для функций + явная проверка владения/членства на объекте (это ABAC-lite) + allow-list полей на чтение и запись для каждой роли. Правила — в одном модуле (ядре), не размазаны по контроллерам.

## Где живёт решение

- **Одно место.** Функция `can(subject, action, resource)` или слой политик. Контроллеры вызывают её, не повторяют логику. Клиент не решает ничего, он только скрывает кнопки.
- **Ближе к данным.** Авторизация в сервисе ядра, а не в HTTP-слое; RLS в Postgres как второй эшелон (см. `d9` и `stack-notes.md`).
- **Deny by default.** Нет правила → отказ. Новый эндпоинт без аннотации доступа — не компилируется / не регистрируется / падает тест.
- **Решение после загрузки объекта.** Загружать объект по `id` **и** `owner_id/community_id` из сессии в одном запросе (`WHERE id = $1 AND community_id = $2`): тогда чужой объект «не существует». Не загружать по `id`, а потом сравнивать — забывают.
- **Policy as code**, если правил больше десятка: OPA/Rego, Cedar, Casbin, Oso. Политики тестируются как код.

## Изоляция арендаторов и сообществ

Продукт с несколькими сообществами (арендаторами) обязан гарантировать: данные одного не видны другому ни через список, ни через объект, ни через поиск, ни через ассистента, ни через агрегаты.

- **Идентификатор арендатора — из сессии, никогда из запроса.** Если `community_id` приходит в теле, сервер сверяет его с членством, а не доверяет.
- **Каждый запрос к данным фильтруется по арендатору.** Паттерн «репозиторий принимает контекст арендатора обязательным параметром» делает забывание невозможным по типу.
- **RLS в Postgres**: `SET LOCAL app.community_id` на транзакцию и политики `USING (community_id = current_setting('app.community_id')::uuid)`. Роль приложения без `BYPASSRLS`. Это ловит ошибки в коде ядра.
- **Общие ресурсы**: кэш, очереди, индексы поиска, embedding-хранилище — ключ или фильтр по арендатору. Ассистент и ранжирование видят только обезличенные тексты своего сообщества.
- **Агрегаты и счётчики** («в сообществе 37 человек ищут X») — проверь, что не раскрывают наличие конкретного человека (LINDDUN: Detecting).
- **Кросс-арендаторные сущности** (один человек в двух сообществах) — явная модель: профиль общий, данные активности — по сообществу.

## Идентификаторы

Последовательные целые `id` делают перебор тривиальным и раскрывают объёмы. UUIDv4/ULID/UUIDv7 — непредсказуемы, но **не заменяют авторизацию**: ссылка утечёт в лог, Referer, скриншот. Непредсказуемый id — защита от перебора, проверка на объекте — защита от доступа.

## Поля: чтение и запись

- **Чтение**: DTO/сериализатор на выход для каждой роли и состояния. Контакт появляется в ответе только когда ядро сказало «обе стороны согласились». «Удалить поле на клиенте» — не защита.
- **Запись**: allow-list полей на каждый эндпоинт; статусные поля (`status`, `role`, `owner_id`, `community_id`, `verified`) меняются только через выделенные операции с собственными правилами.
- **GraphQL**: авторизация на каждом резолвере, не на корне; лимит глубины и сложности; introspection выключен в проде; `__typename`-перебор.

## Эскалация привилегий

Вертикальная (участник → админ): флаг роли из запроса, mass assignment, админ-эндпоинт без проверки, JWT с ролью без перепроверки, инвайт-ссылка с ролью в параметре. Горизонтальная (участник → другой участник): IDOR, предсказуемые id, утечка через связанные объекты (`/offers/:id/messages` проверяет оффер, но не сообщение). Защита: роли из БД при каждом запросе (или короткий токен с версией), проверка всей цепочки владения, отдельный аудит на изменение ролей.

## Админ-поверхности

Отдельный origin или префикс с отдельной аутентификацией и MFA; allow-list IP/VPN как дополнение; каждый админ-запрос в аудит-лог с субъектом, объектом, до/после; действия над данными пользователя — с причиной; «посмотреть как пользователь» — явная сессия с пометкой, ограниченная по времени, без права совершать действия от имени.

## Согласия и двусторонние действия

Действие, требующее двух согласий (раскрытие контакта, сделка, передача владения), моделируется как состояние с переходами, где каждый переход проверяет актора и текущее состояние **атомарно** (`UPDATE … WHERE status = 'pending' AND responder_id = $me`), иначе гонка позволяет «согласиться за другого» или дважды. Отзыв согласия — тоже переход с правилами. Подробно про гонки — `d11`.

## Тесты авторизации

Для каждого эндпоинта с объектом — минимум три теста: владелец видит; чужой из того же сообщества не видит (404/403 — одинаково с «не существует»); чужой из другого сообщества не видит. Плюс: аноним → 401; роль ниже → 403 на функцию; попытка записать защищённое поле → игнор или 400. Матрица «роль × действие × объект» как таблица в тестах. Без таких тестов контроль исчезнет при рефакторинге.

## Вопросы для брейншторма

1. Для каждого эндпоинта фичи: что проверяем на функции, объекте, полях? Где в коде?
2. Откуда берётся `community_id`/`owner_id` при каждом запросе: из сессии или из запроса?
3. Что увидит пользователь, подставив чужой id в URL, тело, заголовок, параметр фильтра?
4. Какие поля ответа появляются только после события (согласие, оплата)? Кто это решает?
5. Какие поля можно записать, и есть ли среди них статусные?
6. Какие общие хранилища (кэш, поиск, очередь, эмбеддинги) не разделены по сообществу?
7. Как меняется роль? Кто это может, что логируется?
8. Есть ли RLS или иной второй эшелон, если ядро ошибётся?
9. Есть ли тест «чужой не видит» на каждый объектный эндпоинт?
10. Какие действия необратимы и требуют двух условий (два согласия, MFA, два человека)?

## Признаки проблемы

Проверка только `isAuthenticated` · загрузка по `id` без фильтра владельца · `community_id` в теле запроса · контакт в JSON с флагом `visible: false` · роль в JWT без перепроверки · админ-роуты под общей аутентификацией · нет теста на чужой доступ · GraphQL с авторизацией на корне.
