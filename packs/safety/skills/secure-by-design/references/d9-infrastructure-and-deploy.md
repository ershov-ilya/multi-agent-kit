# D9. Инфраструктура и выкладка

> Самое частое — не хитрая уязвимость, а дефолтный конфиг, лишний открытый порт, процесс под root и непоставленный патч. Security Misconfiguration поднялась на второе место OWASP 2025.

OWASP A02:2025 Security Misconfiguration; CWE-16, CWE-276 (неверные права по умолчанию), CWE-1188 (небезопасные дефолты), CWE-250 (выполнение с лишними привилегиями). CIS Benchmarks (Linux, nginx, PostgreSQL, Docker), NIST SP 800-207 (Zero Trust), NIST SP 800-123 (харденинг серверов). ASVS 5.0: V13 Configuration.

## Модель: что открыто, кто запущен, что обновлено

Три вопроса покрывают 80 % инфраструктурных проблем:
1. **Что открыто наружу?** Каждый порт, каждый домен, каждый путь. `ss -tlnp`, внешний скан (`nmap`), inventory DNS.
2. **Под кем работает?** Каждый процесс — пользователь ОС, роль БД, права на файлы, capabilities.
3. **Когда обновлялось?** ОС, nginx, Node, Postgres, Docker, зависимости, сертификаты.

## Хост (Linux)

- **Пользователи**: отдельный непривилегированный пользователь на каждое приложение (`api`, `web`, `backup`); `sudo` только по необходимости, с логом; без общих учёток; root-вход по SSH выключен.
- **SSH**: только ключи (`PasswordAuthentication no`), `PermitRootLogin no`, современные алгоритмы, `AllowUsers`, fail2ban/sshguard, нестандартный порт — не защита, а шум; ключи с passphrase; `~/.ssh/authorized_keys` с `from=`/`command=` для deploy-ключей; ротация ключей при уходе людей.
- **Файрвол**: deny by default (`ufw`/`nftables`): открыты 22 (ограничить по IP, если возможно), 80, 443; Postgres, Redis, PM2-порты, метрики, админки — только localhost или private-сеть. Проверять снаружи, не только изнутри.
- **Обновления**: `unattended-upgrades` для безопасности, окно перезапуска, уведомления; kernel livepatch или плановые ребуты.
- **Права файлов**: конфиги с секретами `600`, каталог приложения не писаем процессом приложения (кроме явных `uploads/`, `tmp/`), `umask 027`.
- **Лишнее**: удалить ненужные сервисы, компиляторы на проде не обязательны, `apt autoremove`.
- **Время**: NTP; без него ломаются TLS, TOTP и логи.
- **Аудит**: `auditd` или хотя бы `journald` с отправкой наружу; алерт на новый `sudo`, новый пользователь, изменение `authorized_keys`.
- **CIS Benchmark** для дистрибутива как чеклист; Lynis для быстрого аудита.

## Процессы (PM2, systemd, контейнеры)

- Не root. PM2 под пользователем приложения; systemd-юниты с `User=`, `NoNewPrivileges=true`, `ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true`, `ReadWritePaths=` только нужные, `CapabilityBoundingSet=` пустой, `MemoryMax=`, `TasksMax=`.
- Секреты через `EnvironmentFile=` с правами 600 или `LoadCredential=`; не в юните и не в `ecosystem.config.js` в git.
- Лимиты: память, файловые дескрипторы, рестарт с backoff; health-check.
- Логи — в journald/файлы с ротацией, без секретов (см. `d10`).
- Контейнеры: `USER` не root, read-only rootfs, `--cap-drop=ALL`, `no-new-privileges`, без `--privileged`, без монтирования docker-сокета, сети по назначению, лимиты ресурсов, образы по digest, сканирование.

## nginx (edge)

- TLS 1.3/1.2, ACME-сертификаты с автообновлением, HSTS, OCSP stapling, редирект 80→443.
- Заголовки безопасности (см. `d2`): CSP, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `frame-ancestors`.
- `server_tokens off`; убрать дефолтный сервер или сделать его `444`; `default_server` с самоподписанным сертификатом, чтобы по IP не отдавать продукт.
- Лимиты: `client_max_body_size`, `limit_req` (зоны по IP для `/auth/*`), `limit_conn`, таймауты (`client_body_timeout`, `send_timeout`), размер заголовков.
- Проксирование: `proxy_set_header X-Forwarded-For`/`X-Real-IP` только от доверенного edge; приложение доверяет `X-Forwarded-*` только с localhost (`trustProxy` с явным списком).
- Статика: запрет `.git`, `.env`, `*.map` (если не нужны), скрытых файлов; `autoindex off`; правильный `Content-Type` и `nosniff`.
- Отдельный `server` для пользовательского контента (другой домен).
- Проверка: `nginx -t`, Mozilla SSL Config Generator, SSL Labs, securityheaders.com.

## Postgres

- Роли: отдельная роль на каждое приложение (`api_app`, `backup_ro`), без `SUPERUSER`, без `CREATEDB`, без `BYPASSRLS`; владелец схемы ≠ роль приложения; миграции — отдельной ролью.
- `pg_hba.conf`: `scram-sha-256`, локальные подключения через unix-socket с `peer`/паролем, сеть — только с `ssl` и конкретных адресов; никакого `trust`, никакого `0.0.0.0/0`.
- `listen_addresses` — `localhost`, если приложение рядом.
- Привилегии: `REVOKE ALL ON SCHEMA public FROM PUBLIC`; `GRANT` только нужные таблицы и действия; схемы по владельцу (`core`, `auth`) с разделением.
- **RLS** как второй эшелон изоляции сообществ (см. `d4`): `ALTER TABLE … ENABLE ROW LEVEL SECURITY; FORCE ROW LEVEL SECURITY`; политика по `current_setting('app.community_id')`; роль приложения без `BYPASSRLS`.
- `statement_timeout`, `idle_in_transaction_session_timeout`, `max_connections` под пул.
- Логи: `log_connections`, `log_disconnections`, `log_statement = 'ddl'`, без `log_statement = 'all'` в проде (ПДн в логах); `log_min_duration_statement` для медленных.
- Расширения — минимум; `dblink`/`file_fdw`/`COPY TO PROGRAM` — только суперпользователю.
- Бэкап: `pg_dump` под отдельной read-only ролью, шифрование `age`, перенос на другой хост, проверка восстановления, ротация, журнал (см. `d6`, `d7`). Бэкап-хост — минимальные права, отдельные ключи.
- Обновления minor-версий — регулярно.

## Redis, очереди, кэш

Только localhost/unix-socket или TLS + `requirepass`/ACL; `rename-command` для `FLUSHALL`/`CONFIG`; `protected-mode yes`; ключи с префиксом арендатора; TTL на всё.

## Сеть и DNS

- Сегментация: edge → приложение → данные; данные недоступны с edge напрямую.
- Исходящий трафик: allow-list, если возможно (egress-фильтр против SSRF и утечки), хотя бы запрет на metadata-адреса.
- DNS: CAA-запись (кто может выпускать сертификаты), DNSSEC, нет «висящих» записей на удалённые хосты (subdomain takeover).
- Почта с домена: SPF (`-all`), DKIM, DMARC (`p=reject` после мониторинга), MTA-STS/TLS-RPT; иначе письма с кодами входа попадают в спам, а домен подделывают для фишинга.
- `security.txt` на `/.well-known/security.txt` с контактом для исследователей.

## DoS и доступность

Лимиты на edge (`limit_req`), на приложении (по пользователю), на БД (`statement_timeout`); CDN/анти-DDoS перед хостом, если продукт публичный; защита дорогих эндпоинтов (поиск, LLM, отправка писем) отдельными лимитами и очередями; мониторинг и алерт на всплески; план деградации (отключить дорогие функции, сохранить вход и чтение).

## WAF и сканеры

WAF (ModSecurity + OWASP CRS, облачные) — дополнительный шум-фильтр против известных сигнатур, не замена кода. Ставить в режим detect, затем block для явных правил. Регулярно: внешний скан портов, `testssl.sh`, OWASP ZAP baseline по проду, проверка заголовков.

## Среда и конфигурация как код

- Конфиг в репозитории (без секретов), секреты отдельно; ревью изменений конфига как кода.
- Prod/staging/dev различаются только секретами и адресами; debug-флаги, playground, introspection, `NODE_ENV=development` в проде невозможны по конструкции.
- Сборка на хосте под пользователем деплоя, деплой-ключ read-only, сверка версии/тега, откат за минуту.
- Инвентарь: что где запущено, какой версии, кто владелец, когда обновлялось. Один файл в `ops/`.

## Облако (если применимо)

IAM-роли с минимальными правами на ресурс, не на аккаунт; MFA на всех учётках консоли; корневая учётка не используется; бакеты приватные по умолчанию, block public access; IMDSv2; CloudTrail/аудит-лог включён; бюджетные алерты (DoS по счёту).

## Вопросы для брейншторма

1. Какие порты, домены и пути открыты наружу после выкладки фичи? Нужны ли все?
2. Под каким пользователем ОС и ролью БД работает новый процесс/воркер? Что он может сверх задачи?
3. Какие новые секреты появляются на хосте и где они лежат?
4. Какие лимиты на edge для новых эндпоинтов?
5. Доверяет ли приложение `X-Forwarded-*` только от своего edge?
6. Что в `pg_hba.conf` и какие гранты у роли приложения на новые таблицы? Нужна ли RLS?
7. Как узнаем, что на хосте появился новый пользователь, ключ, sudo?
8. Что произойдёт при DoS на дорогой эндпоинт: деградация или падение всего?
9. Когда последний раз обновляли ОС, nginx, Node, Postgres? Кто за это отвечает?
10. Есть ли `security.txt`, SPF/DKIM/DMARC, CAA?

## Признаки проблемы

Postgres слушает `0.0.0.0` · `trust` в `pg_hba` · PM2 под root · `.env` рядом с кодом с правами 644 · `server_tokens on` · нет `limit_req` на `/auth` · `X-Forwarded-For` от кого угодно · Redis без пароля · SSH по паролю · `FROM node:latest` · DMARC `p=none` навсегда.
