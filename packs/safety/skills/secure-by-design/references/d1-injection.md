# D1. Ввод и инъекции — где данные становятся кодом

> Инъекция — это не «плохие символы». Это ситуация, когда строка, собранная из ввода, попадает в интерпретатор, который не отличает данные от команд. Защита одна: дать интерпретатору данные и команду раздельно.

OWASP A05:2025 Injection; CWE-89 (SQL, #2 в CWE Top 25:2025), CWE-78 (OS command), CWE-94 (code injection), CWE-22 (path traversal), CWE-502 (deserialization), CWE-611 (XXE), CWE-1333 (ReDoS), CWE-915 (mass assignment), CWE-1321 (prototype pollution). ASVS 5.0: V1 Encoding and Sanitization, V2 Validation and Business Logic, V5 File Handling.

## Общая модель

1. **Источники**: параметры URL и тела, заголовки, cookie, файлы и их имена, поля из БД (second-order), ответы чужих API, вебхуки, сообщения бота, вывод LLM, переменные окружения, аргументы CLI.
2. **Стоки (интерпретаторы)**: SQL, NoSQL-запросы, shell, шаблонизатор, файловая система, LDAP/XPath, XML-парсер, десериализатор, регулярное выражение, HTML/JS (см. D2), заголовки HTTP, лог, email-заголовки, LLM-промпт (см. D12).
3. **Защита по приоритету**: (а) отделить данные от кода механизмом интерпретатора — параметры, API без строки; (б) allow-list структуры ввода (тип, длина, диапазон, перечень); (в) кодирование под контекст стока; (г) наименьшие привилегии у интерпретатора; (д) обнаружение — лог и алерт на аномалии. Чёрный список символов — не защита, только шум.

## Карта инъекций

| Класс | Сток | Как выглядит | Канонический контроль | Чего не делать |
|---|---|---|---|---|
| **SQL** (CWE-89) | SQL-драйвер | `'1' OR '1'='1`, `UNION SELECT`, `; DROP`, слепые по времени `pg_sleep` | Параметризованные запросы `$1`, prepared statements, ORM/билдер с параметрами; для имён таблиц/колонок и `ORDER BY` — allow-list из кода; роль БД без DDL и без доступа к чужим схемам | Конкатенация, `format()` со значениями, экранирование вручную, «только числа» через `parseInt` без проверки `NaN` |
| **NoSQL** | Mongo, Elastic, Redis | `{"$gt": ""}` вместо строки, операторы в ключах | Схема ввода: тип поля строго примитив; запрет ключей с `$` и `.`; параметризованные Redis-команды | Прокидывать объект из JSON в запрос |
| **ORM/билдер** | Raw-методы ORM | `.raw()`, `.whereRaw()`, `sequelize.literal()`, интерполяция в `sql\`\`` | Только плейсхолдеры даже в raw; тег-шаблоны, которые параметризуют (`sql` из postgres.js, `pg-format` для идентификаторов) | Считать ORM защитой автоматически |
| **Команды ОС** (CWE-78) | `sh -c` | `; rm -rf`, `$(...)`, backticks, `|` | Не вызывать shell: `execFile`/`spawn` с массивом аргументов, без `shell: true`; allow-list значений; библиотека вместо утилиты | `exec` со строкой, экранирование кавычек |
| **Инъекция аргументов** | CLI утилиты | Значение начинается с `-`: `--output=/etc/passwd` | `--` перед позиционными аргументами, проверка первого символа, allow-list | Доверять, что «аргумент, а не команда» безопасен |
| **Шаблоны (SSTI)** (CWE-1336) | Jinja2, Twig, Freemarker, EJS, Handlebars | `{{7*7}}` → 49; через шаблон до RCE | Пользовательские данные — только как переменные шаблона, никогда как сам шаблон; «безопасные» движки без доступа к объектам (Mustache-подобные) для пользовательских шаблонов; sandbox | Собирать шаблон конкатенацией, давать пользователю писать шаблон на полном движке |
| **Путь к файлу** (CWE-22) | FS | `../../etc/passwd`, `%2e%2e/`, абсолютный путь, симлинк, NUL-байт | Идентификатор вместо имени файла (id → путь из таблицы); нормализация и проверка, что результат внутри базового каталога; allow-list символов имени; отдельный пользователь ОС без доступа к чужим каталогам | Строковая проверка на `..` без нормализации |
| **LDAP / XPath** | Каталог, XML-запросы | `*)(uid=*))(|(uid=*` | Экранирование по RFC 4515 для LDAP, параметризованный XPath (XPath 2+ variables) | Конкатенация фильтра |
| **Заголовки HTTP / CRLF** (CWE-113) | HTTP-ответ, email | `\r\nSet-Cookie:`, `\r\n\r\n<html>` | Запрет CR/LF в значениях заголовков (фреймворки обычно режут, проверь); для email — библиотека с валидацией адресов и заголовков | Вставлять ввод в `Location`, `Content-Disposition`, `To:` без проверки |
| **Лог-инъекция** (CWE-117) | Лог-файл, SIEM | `\n[INFO] admin logged in`, ANSI-коды, JSON-разрыв | Структурированные логи (JSON) с экранированием; обрезка длины; удаление управляющих символов | Писать ввод в текстовую строку лога |
| **XXE** (CWE-611) | XML-парсер | `<!ENTITY xxe SYSTEM "file:///etc/passwd">`, billion laughs | Отключить внешние сущности и DTD; предпочесть JSON; лимит глубины/размера | Парсить XML дефолтным парсером старого стека |
| **Десериализация** (CWE-502) | `pickle`, Java `ObjectInputStream`, PHP `unserialize`, YAML `load`, `node-serialize` | Объект с «магическим» методом исполняет код при разборе | Только форматы данных (JSON, protobuf, msgpack) со схемой; подпись сериализованного (HMAC) если формат родной; allow-list классов | Десериализовать объекты из cookie, очереди, кэша без подписи |
| **Code injection** (CWE-94, CWE-95) | `eval`, `Function`, `vm`, `exec` | Ввод попадает в выполняемый код | Не выполнять строки; интерпретатор выражений с allow-list операций; sandbox как последний рубеж, с пониманием, что `vm` в Node — не песочница | «Мини-язык формул» на `eval` |
| **ReDoS** (CWE-1333) | Регулярные выражения | `(a+)+$` на `aaaaaaaaaaaaaaaaaaaaaaaa!` — экспоненциальный backtracking | Линейные движки (RE2, Rust `regex`), ограничение длины ввода, таймаут, проверка regex линтером (`safe-regex`, `recheck`) | Регулярки из пользовательского ввода; вложенные квантификаторы |
| **Mass assignment** (CWE-915) | ORM / модель | `{"name": "x", "is_admin": true}` | Allow-list полей на запись для каждого эндпоинта (DTO/схема), отдельные схемы для создания и обновления | `Model.update(req.body)` |
| **Prototype pollution** (CWE-1321) | JS-объекты | `{"__proto__": {"isAdmin": true}}`, `constructor.prototype` | Схемная валидация с запретом лишних ключей; `Object.create(null)` для словарей; `Map`; обновлённые lodash/merge-библиотеки; `--disable-proto=delete` | Глубокий merge ввода в конфиг |
| **Форматные строки / интерполяция логгера** | `printf`, `util.format`, `%s` | `%n`, `%x` | Формат — константа, значения — аргументы | Передавать ввод первым аргументом `format` |
| **Email-инъекция** | SMTP-заголовки, шаблон письма | Доп. получатели через `\n`, HTML в письме | Библиотека с валидацией, текстовые письма или кодирование под HTML, адреса из allow-list | Склеивать заголовки строками |
| **Second-order** | Любой | Полезная нагрузка сохраняется «чисто», а срабатывает при чтении в другом контексте | Защищать сток, а не вход: параметризовать при каждом использовании, кодировать при каждом выводе | «Мы уже проверили при сохранении» |

## Валидация ввода правильно

- **Схема на границе.** Каждый эндпоинт описан схемой (JSON Schema/zod/serde): тип, обязательность, длина, диапазон, формат, перечень, запрет неизвестных полей (`additionalProperties: false`). Невалидный → 400 с кодом, без эха ввода.
- **Allow-list, не deny-list.** Перечень допустимого, а не перечень запрещённого.
- **Каноникализируй до проверки.** Unicode NFC, декодирование URL один раз, нормализация пути, lowercase для email-домена. Проверка после нормализации, использование — того же нормализованного значения.
- **Длина — везде.** Строки, массивы, глубина JSON, размер тела, количество файлов. Это и анти-DoS.
- **Числа — как числа.** Диапазон, целочисленность, `NaN`/`Infinity`/`-0`, переполнение в 32-бит БД.
- **Идентификаторы — непредсказуемые и типизированные.** UUIDv4/ULID, проверка формата до запроса к БД.
- **Валидация — не санитизация.** Валидация отбрасывает, санитизация изменяет. Санитизируй только там, где нельзя отбросить (HTML из редактора — через DOMPurify с allow-list), и понимай, что меняется семантика.
- **Валидация не заменяет параметризацию.** Валидный ввод всё равно уходит в SQL параметром.

## Кодирование вывода под контекст

Один и тот же символ `<` безопасен в SQL и опасен в HTML; `'` наоборот. Кодируй непосредственно перед стоком, по его правилам: HTML-тело, HTML-атрибут, JS-строка, URL-параметр, CSS, SQL-идентификатор, shell-аргумент, LDAP-фильтр. Подробно для браузера — `d2-browser-and-web.md`.

## Файлы: загрузка и обработка (ASVS V5)

- Имя файла — не доверять: генерировать своё, хранить оригинал как метаданные с экранированием.
- Тип — по содержимому (magic bytes), не по расширению и не по `Content-Type` клиента; allow-list типов.
- Размер — лимит до чтения тела; количество — лимит на пользователя.
- Хранить вне веб-корня или в объектном хранилище; отдавать с `Content-Disposition: attachment`, своим `Content-Type`, `X-Content-Type-Options: nosniff`, с отдельного домена (sandbox-домен), чтобы SVG/HTML не выполнялись в origin приложения.
- Изображения — перекодировать (strip EXIF, пересоздать битмап), это и приватность (геометки), и защита от полиглотов.
- Архивы — zip-slip (`../` внутри архива), zip-бомбы: лимит распакованного размера и проверка путей.
- Обработчики (ImageMagick, ffmpeg, libreoffice) — отдельный процесс, отдельный пользователь, таймаут, лимит памяти, свежие версии.

## Вопросы для брейншторма

1. Перечисли все стоки фичи: SQL, FS, shell, шаблон, регулярка, лог, email, LLM. Для каждого — как данные отделены от команды?
2. Есть ли место, где имя таблицы, колонки, поле сортировки или путь строится из ввода? Где allow-list?
3. Какие поля клиент может прислать лишние, и что сделает модель с `is_admin`, `community_id`, `owner_id`?
4. Какие регулярки применяются к вводу, и есть ли у них вложенные квантификаторы? Какой лимит длины?
5. Что из ввода попадает в лог, и как структурирован лог?
6. Что сохраняется сейчас, а интерпретируется позже (second-order)? Защищён ли сток при чтении?
7. Файлы: по чему определяем тип, где храним, с какого домена отдаём, перекодируем ли?
8. Какие привилегии у интерпретатора при успешной инъекции: роль БД, пользователь ОС, сеть?

## Признаки проблемы

Строка SQL с `+` или `${}` · `exec(` со строкой · `eval` · `Model.update(req.body)` · `new RegExp(userInput)` · `path.join(base, userInput)` без проверки результата · XML-парсер без отключения DTD · `yaml.load` вместо `safeLoad` · поле сортировки из query без allow-list.
