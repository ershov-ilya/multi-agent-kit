# Плейбук сессии безопасности

Как вести брейншторм, RFC, ревью или аудит по карте доменов из `SKILL.md`. Файл задаёт процесс; содержание угроз и контролей лежит в файлах доменов `d1`–`d13`.

## Шесть режимов

| Режим | Когда | Вход | Выход |
|---|---|---|---|
| **RFC / брейншторм** | Новая фича, продукт, интеграция ещё на бумаге | Описание фичи, экраны, API, данные | Модель угроз фичи, контроли, раздел «Безопасность» для RFC, пункты в чеклист релиза |
| **Дизайн-ревью** | RFC написан, код ещё нет | Текст RFC/ADR, схема потоков | Список замечаний с риском и исправлением, вердикт «можно строить / доработать» |
| **Код-ревью** | PR или модуль | Diff, контекст модуля | Находки: файл, строка, CWE, сценарий, фикс, серьёзность |
| **Аудит существующего** | Сервис живёт, безопасность никто не проектировал | Доступ к коду, конфигам, схеме БД, инфраструктуре | Карта поверхности, топ рисков, план по приоритету, быстрые победы |
| **Инцидент** | Что-то уже случилось или подозревается | Симптомы, логи, время | Классификация, сдерживание, искоренение, восстановление, уведомления, постмортем (см. `d10`) |
| **Короткий вопрос** | «Чем хешировать?», «нужен ли CSRF-токен?» | Вопрос | Прямой ответ со стандартом и типичной ошибкой |

Гибрид — норма: «RFC с кусками кода» ведётся как RFC, код смотрится по ходу.

## Что собрать до начала

Без этого модель угроз будет про абстрактный сервис, а не про ваш.

1. **Актив.** Что теряем при компрометации: персональные данные (какие именно), контакты, деньги, репутация, доступность. Оцени ущерб словами: «один пользователь увидит чужой телефон» против «выгружена вся база».
2. **Противник.** Реалистичные профили, 2–4 штуки: любопытный пользователь, обиженный участник, спамер с ботами, конкурент, инсайдер с доступом к серверу, автоматический сканер. Для каждого: что умеет, чего хочет, сколько готов потратить.
3. **Границы доверия.** Клиент (не доверяем), API (вход), ядро (решает), БД, внешние сервисы (почта, Telegram, LLM, CDN), админ, CI/CD, бэкап. Каждая стрелка через границу — точка проверки.
4. **Поток данных.** Откуда входит, где решается, где хранится, куда уходит, где логируется. Отдельно — где лежат секреты.
5. **Ограничения.** Регуляторика (ПДн, 152-ФЗ/GDPR, дети, платежи), стек, один хост или кластер, есть ли команда реагирования. Пилоту на одном хосте — ASVS L1 плюс критичные пункты L2 для входа и доступа.

Если чего-то нет — сформулируй допущение явно и пометь, что его стоит подтвердить.

## Алгоритм по шагам

### Шаг 1. Поверхность атаки
Выпиши все входы: HTTP-эндпоинты, вебхуки, загрузки файлов, параметры URL, заголовки, cookie, сообщения из бота, ответы внешних API, данные из БД, промпты для LLM, CLI-аргументы, файлы конфигурации. Для каждого: кто может туда писать.

### Шаг 2. Границы и STRIDE
Для каждой границы доверия пройди шесть вопросов (подробно в `principles-and-threat-modeling.md`):

| Буква | Вопрос |
|---|---|
| S Spoofing | Может ли кто-то прикинуться другим пользователем, сервисом, вебхуком? |
| T Tampering | Может ли кто-то изменить данные по пути или в хранилище? |
| R Repudiation | Сможем ли доказать, кто что сделал? |
| I Information disclosure | Что утечёт тому, кому не положено? |
| D Denial of service | Как это положить или сделать дорогим? |
| E Elevation of privilege | Как получить больше прав, чем выдано? |

Угрозу записывай строкой: «кто → что делает → с чем → последствие». Для ПДн пройди LINDDUN (связывание, идентификация, неотказуемость, обнаружение, раскрытие, неосведомлённость, несоблюдение).

### Шаг 3. Проход по доменам
Выбери ведущие домены фичи (обычно 3–5). Открой файл каждого, пройди раздел «Вопросы для брейншторма». Остальные домены пройди по таблице в `SKILL.md`: одна строка «угроза» или «не применимо, потому что».

Типичные ведущие домены по типу фичи:

| Фича | Ведущие домены |
|---|---|
| Вход, регистрация, восстановление | D3, D11, D10, D7 |
| Профиль, настройки, контакты | D4, D7, D1, D2 |
| Список, поиск, выдача | D4, D11, D1, D5 |
| Оффер, согласие, раскрытие контакта | D4, D11, D10, D7 |
| Загрузка файла, аватар | D1, D2, D9, D7 |
| Платёж, баланс, промокод | D11, D4, D10, D6 |
| Вебхук, интеграция, бот | D5, D6, D3, D1 |
| Ассистент на LLM, ранжирование | D12, D7, D4, D10 |
| Админка, модерация | D4, D3, D10 |
| Бэкап, миграция, экспорт | D7, D6, D9, D10 |
| Новая зависимость, CI-пайплайн | D8, D9, D6 |

### Шаг 4. Оценка риска
Вероятность (1–3: нужен инсайдер / нужен навык / делает сканер) × ущерб (1–3: один пользователь / группа / вся база или деньги). 7–9 — блокер релиза, 4–6 — до конца пилота, 1–3 — реестр. Для конкретной найденной уязвимости — CVSS 4.0.

### Шаг 5. Контроли с эшелонами
Для каждой угрозы с риском 4+ назначь четыре слоя: предотвратить, ограничить ущерб, обнаружить, восстановить. Каждому контролю — тест, который падает при его исчезновении, и владелец. Контроль без теста исчезнет при рефакторинге.

### Шаг 6. Проверка принципов
Deny by default · least privilege · fail closed · решение на сервере в одном месте · минимизация данных · нет самодельной криптографии · параметризация вместо фильтрации · короткие секреты живут коротко · логируем событие, не данные. Нарушение любого — красный флаг.

### Шаг 7. Выдача
Сводка, модель угроз, контроли, остаточные риски, тесты, пункты в чеклист релиза, готовый раздел «Безопасность» для RFC.

## Шаблон раздела «Безопасность» для RFC

Короткий, 10–25 строк, чтобы его читали. Детали — в модели угроз рядом.

```
## Безопасность

**Актив.** <что защищаем одной фразой>
**Противник.** <2–3 профиля>

**Границы и проверки.**
- <граница>: <кто проверяет, что именно, где в коде>
- …

**Главные угрозы и контроли.**
1. <угроза> → <контроль>, стандарт <OWASP/ASVS/CWE>, тест <имя>
2. …

**Данные.** Какие ПДн появляются, где хранятся, срок жизни, как удаляются, что из этого попадает в логи и бэкап.

**Не делаем в этом RFC и почему.** <остаточные риски, принятые осознанно>

**Чеклист релиза.** <3–7 пунктов>
```

## Пример мини-сессии: «вход по одноразовому коду на почту»

**Контекст.** Актив: доступ к аккаунту и контактам, которые открываются после согласия. Противник: любопытный пользователь с чужим email; бот, перебирающий коды; спамер, использующий отправку кодов как бесплатную рассылку. Границы: клиент → API `/auth/code` и `/auth/verify` → хранилище кодов → почтовый провайдер.

**STRIDE по границе клиент → API.**
- S: подмена получателя — ввести чужой email и перехватить код? Код уходит только на указанный адрес; без доступа к почте бесполезен.
- T: подмена кода — перебор 6 цифр = 10⁶ вариантов; без лимита перебор за минуты.
- R: нет журнала попыток — не докажем, что аккаунт взломан перебором.
- I: ответ «такого пользователя нет» раскрывает базу email.
- D: запрос кода без лимита — счёт у почтового провайдера и блокировка домена за спам.
- E: код одного пользователя принимается для другого при ошибке привязки.

**Контроли (D3, D11, D10).**
1. Код 6 цифр из CSPRNG, TTL 10 минут, одноразовый, хранится как хеш, привязан к email и к попытке запроса. Тест: повторное использование → 400.
2. Лимит проверок: 5 попыток на код, затем код сгорает; лимит на email и на IP для выдачи кодов (например, 3 в 10 минут, 10 в сутки). Тест: шестая попытка → 429 и код недействителен.
3. Одинаковый ответ на запрос кода независимо от существования аккаунта, одинаковое время. Тест: сравнение ответов и p95 времени.
4. Журнал событий: запрос кода, успех, провал, блокировка, с user_id/email-хешем и IP, без самого кода. Алерт при всплеске провалов.
5. Сессия после входа: серверная, httpOnly+Secure+SameSite cookie, ротация id при входе, срок жизни и выход везде.

**Остаточное.** Доступ к почтовому ящику = доступ к аккаунту. Принимаем для пилота; passkey как второй фактор — после.

**В чеклист релиза.** Лимиты включены в проде; алерт настроен; тест на перебор в CI; письмо с кодом не попадает в логи провайдера в открытом виде (проверить настройки).
