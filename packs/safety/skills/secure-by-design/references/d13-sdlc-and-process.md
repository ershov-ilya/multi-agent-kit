# D13. Процесс: безопасность в SDLC

> Всё из доменов D0–D12 исчезнет через два релиза, если его не держит процесс: требования, тесты, автоматические проверки, владелец. Безопасность — не проект, а свойство конвейера.

OWASP SAMM 2.0, OWASP ASVS 5.0 (уровни L1–L3), NIST SSDF (SP 800-218), BSIMM, CISA Secure by Design, ISO/IEC 27034. Инструменты: SAST, SCA, DAST, IAST, secret scanning, fuzzing, пентест, bug bounty.

## Уровни ASVS как цель

| Уровень | Для кого | Что требует |
|---|---|---|
| **L1** | Любое приложение, минимальная планка | Базовые контроли: валидация, авторизация на объект, безопасная аутентификация, TLS, заголовки, логирование; проверяемо снаружи |
| **L2** | Приложения с ПДн, деньгами, доверием (большинство продуктов) | Всё L1 плюс защита по дизайну, криптография, управление сессиями углублённо, защита от бизнес-логических атак; нужен доступ к коду/дизайну |
| **L3** | Критичные: медицина, финансы, инфраструктура | Всё L2 плюс углублённая архитектурная верификация, моделирование угроз на каждом изменении |

Практика для пилота с ПДн: L1 целиком плюс критичные L2-требования для V6–V8 (аутентификация, сессии, авторизация) и V14 (данные). ASVS — чеклист для ревью и приёмки, не для чтения целиком.

## OWASP SAMM: пять функций, пятнадцать практик

Governance (стратегия, политика, обучение) · Design (требования, архитектура, моделирование угроз) · Implementation (сборка, деплой, управление дефектами) · Verification (архитектурная оценка, тестирование по требованиям, security testing) · Operations (инциденты, окружение, операционное управление). Оценка 0–3 по каждой практике; цель — не «3 везде», а ровный профиль без нулей. Для маленькой команды: Design и Implementation в первую очередь.

## Требования безопасности в RFC и Definition of Done

Каждый RFC с пользовательским вводом, данными или доступом содержит раздел «Безопасность» (шаблон в `playbook.md`). DoD фичи:
- Модель угроз фичи есть и ревьюилась.
- Тесты авторизации («чужой не видит») на каждый объектный эндпоинт.
- Схема валидации на каждый вход; тест на лишние поля.
- Лимиты включены и протестированы.
- Секреты не в коде; новые — в менеджере, задокументированы.
- Новые зависимости прошли проверку (`d8`).
- События безопасности логируются; алерты и runbook — если фича создаёт новые риски.
- Раздел «Данные» (поле → цель → срок → удаление) заполнен.
- Чеклист релиза (`checklists.md`) пройден.

## Пирамида проверок

| Уровень | Инструмент | Когда | Что ловит |
|---|---|---|---|
| **Pre-commit / IDE** | Линтеры безопасности (eslint-plugin-security, clippy), secret scanning (gitleaks) | На каждом коммите | Секреты, очевидные `eval`/`exec` |
| **CI на PR** | SAST (Semgrep с правилами OWASP/стека, CodeQL), SCA (OSV-Scanner, npm audit, cargo audit), проверка lock-диффа, тесты авторизации и валидации | На каждом PR, блокирует мерж при критичном | Инъекции, небезопасные API, уязвимые пакеты, регрессии контролей |
| **Ночные / по расписанию** | DAST (OWASP ZAP baseline против staging), сканер зависимостей, проверка заголовков и TLS, SBOM-сверка с новыми CVE | Ежедневно/еженедельно | Конфигурация, то, что видно снаружи |
| **По событию** | Fuzzing парсеров и форматов (cargo-fuzz, jazzer), red teaming LLM (`d12`), ревью модели угроз | При изменении парсеров, промптов, границ | Нештатные условия, инъекции в модель |
| **Периодически** | Пентест (внешний, раз в год или перед крупным релизом), аудит инфраструктуры (Lynis, CIS), ревью прав и секретов | Раз в полгода-год | Логика, цепочки, то, что автоматика не видит |
| **Постоянно** | Ответственное раскрытие, bug bounty (когда есть кому отвечать), мониторинг (`d10`) | Всегда | То, что нашли другие |

Правило: инструмент без владельца и без политики реакции — шум. Начинать с трёх: secret scanning, SCA, тесты авторизации. Потом Semgrep. DAST и пентест — когда есть staging и что защищать.

## Код-ревью с фокусом на безопасность

Ревьюер проходит по diff с вопросами: откуда ввод и где сток (`d1`); кто проверил право на объект (`d4`); что попало в лог (`d10`); новые зависимости (`d8`); секреты (`d6`); обработка ошибок и нештатных условий (`d10`); гонки (`d11`); что уходит наружу (`d5`, `d7`). Чеклист в `checklists.md`. Изменения в auth, authz, крипто, миграциях, CI — обязательное второе ревью. PR-шаблон с чекбоксом «есть ли влияние на безопасность, какое».

## ИИ-ассистенты в разработке

- Сгенерированный код ревьюится как чужой PR; те же SAST/SCA.
- Имена пакетов проверяются (slopsquatting, `d8`).
- В промпт не попадают секреты, прод-данные, ПДн.
- Агент в репозитории: без прав на деплой и прод-секреты; действия с побочным эффектом (install, push, деплой) — с подтверждением; инструкции из файлов репозитория и тикетов — данные, не команды (`d12`).
- Ассистент полезен для ревью безопасности: прогон diff по чеклисту, генерация тестов авторизации, объяснение CWE — при условии, что финальное решение за человеком.

## Управление уязвимостями и рисками

- **Реестр рисков**: угроза, актив, риск (В×У), решение (снизить/принять/перенести), владелец, срок, статус. Принятый риск — с датой пересмотра.
- **Дефекты безопасности**: как обычные баги с меткой и SLA по серьёзности (критичные — 24–72 часа, высокие — 2 недели, средние — квартал), с CVSS 4.0 для внешних и В×У для своих.
- **Security debt**: отдельный список, виден в планировании, не растёт бесконтрольно.
- **Инвентарь**: сервисы, эндпоинты (из OpenAPI), зависимости (SBOM), секреты (где, кто, когда ротировать), данные (`d7`), хосты (`d9`). Без инвентаря нет ни реакции на CVE, ни ответа регулятору.
- **Метрики**: время от CVE до патча, доля эндпоинтов с тестами authz, число секретов без ротации > года, покрытие схемами валидации, число открытых критичных.

## Люди и роли

Владелец безопасности (даже если это один человек на полставки); security champion в команде; обучение на своих инцидентах и чужих (постмортемы, OWASP материалы); доступы по принципу наименьших привилегий и отзыв при уходе; offboarding-чеклист (ключи, учётки, секреты, ротация).

## Регуляторика как требование

152-ФЗ: уведомление Роскомнадзора об обработке, локализация, политика обработки ПДн на сайте, согласия, ответ на запросы субъектов, уведомление об утечках, оценка вреда; при определённых условиях — уровни защищённости и меры по приказу ФСТЭК № 21. GDPR при пользователях из ЕС: основание, DPA с процессорами, права субъектов, 72 часа. Платежи: PCI DSS 4.0 — не хранить карточные данные, использовать провайдера. Подробнее — `standards-and-glossary.md`.

## Вопросы для брейншторма

1. Есть ли в RFC раздел «Безопасность» и модель угроз? Кто ревьюит?
2. Какие проверки в CI блокируют мерж? Что из трёх базовых (секреты, SCA, тесты authz) отсутствует?
3. Кто владелец реестра рисков и когда его смотрели последний раз?
4. Как быстро узнаем о новой CVE в зависимости и как быстро выкатим патч?
5. Какие изменения требуют второго ревью? Соблюдается ли?
6. Что из инвентаря (эндпоинты, секреты, данные, хосты) устарело?
7. Когда был последний пентест или внешний взгляд? Что из найденного закрыто?
8. Что делает ИИ-агент в репозитории и с какими правами?
9. Какие регуляторные обязанности есть и выполнены ли базовые (политика, уведомление, DPA)?
10. Что из безопасности исчезнет, если уйдёт один конкретный человек?

## Признаки проблемы

Безопасность «обсудим перед релизом» · нет тестов на чужой доступ · `npm audit` с 40 критичными, которые «не наши» · секреты ротируются «при увольнении, если вспомним» · пентест есть, отчёт лежит · SAST включён, результаты никто не читает · RFC без раздела о данных · ИИ-агент с прод-токеном.
