# D6. Криптография и секреты

> Криптографию не изобретают и не собирают из примитивов вручную. Задача разработчика — правильно выбрать готовую конструкцию под задачу, хранить ключ отдельно от данных и уметь его сменить.

OWASP A04:2025 Cryptographic Failures; CWE-327 (сломанный алгоритм), CWE-328 (слабый хеш), CWE-330 (слабая случайность), CWE-338, CWE-798 (hardcoded credentials), CWE-321, CWE-916 (хеш пароля без растяжения), CWE-347 (нет проверки подписи). ASVS 5.0: V11 Cryptography, V12 Secure Communication.

## Какую задачу решаем

| Задача | Инструмент | Что НЕ подходит |
|---|---|---|
| Проверить целостность файла/артефакта (без противника) | SHA-256, BLAKE3 | MD5, SHA-1 (коллизии) |
| Проверить целостность и авторство при общем секрете | **HMAC**-SHA256 | «SHA-256(secret + msg)» (length extension), просто хеш |
| Авторство без общего секрета | Подпись **Ed25519** (или ECDSA P-256, RSA-PSS ≥ 3072) | RSA PKCS#1 v1.5 для новых систем, DSA |
| Хранить пароль | **Argon2id**, scrypt, bcrypt (см. `d3`) | Любой быстрый хеш, обратимое шифрование |
| Хранить одноразовый код/токен для сравнения | SHA-256 или HMAC с серверным ключом (энтропия уже высока) | Открытый текст |
| Шифровать данные с одним ключом | **AES-256-GCM** или **ChaCha20-Poly1305** (AEAD) с уникальным nonce | AES-ECB, AES-CBC без MAC, свой режим, повтор nonce в GCM |
| Шифровать файл/бэкап для другого получателя | **age** (X25519), libsodium `sealed box`, OpenPGP с современными настройками | Симметричный пароль в скрипте, openssl enc без AEAD |
| Обмен ключами | X25519, ECDH P-256; на практике — TLS 1.3 | DH с малыми группами, своя схема |
| Случайный токен, id сессии, код | CSPRNG: `crypto.randomBytes`/`randomUUID`, `getrandom`, `/dev/urandom`, `rand::rngs::OsRng` | `Math.random`, `rand()`, время, инкремент |
| Защита данных в пути | TLS 1.3 (1.2 допустим), HSTS | Самоподписанные без pinning в проде, отключение проверки сертификата |
| Хранить секреты приложения | Переменные окружения из менеджера секретов, файлы с правами 600, Vault/SOPS/cloud secret manager | Git, код, образ контейнера, логи, URL |

Правило большого пальца: libsodium / `age` / встроенный `crypto` платформы с высокоуровневыми API (`secretbox`, `sealed box`, `crypto.subtle`), а не ручная сборка из AES + HMAC. Если конструкция требует самому выбрать padding, IV, порядок MAC-then-encrypt — это сигнал взять более высокоуровневую библиотеку.

## Параметры, которые забывают

- **Nonce/IV**: для GCM 96 бит, уникальный на каждое шифрование под одним ключом; повтор nonce в GCM раскрывает ключ аутентификации. При большом числе сообщений — XChaCha20-Poly1305 (192-битный случайный nonce) или ротация ключа.
- **Associated data** в AEAD: привязывай шифртекст к контексту (id записи, версия, назначение), чтобы его нельзя было подставить в другое место.
- **Сравнение секретов** — за постоянное время (`crypto.timingSafeEqual`, `subtle::ConstantTimeEq`); `===` утекает по времени.
- **Размер ключей**: AES-256, HMAC-ключ ≥ 256 бит, RSA ≥ 3072, EC P-256/X25519. HS256-секрет для JWT ≥ 256 бит из CSPRNG, не «пароль».
- **Версионируй** формат: `v1:` + nonce + ciphertext, чтобы менять алгоритм без миграции «вслепую».
- **Детерминированное шифрование** (для поиска по зашифрованному) раскрывает равенство; используй осознанно, с отдельным ключом, или blind index через HMAC.

## Ключи и ротация

- **Иерархия**: мастер-ключ (KEK) в менеджере секретов/KMS/HSM или хотя бы в файле вне БД с правами 600; ключи данных (DEK) шифруются KEK — **envelope encryption**. Ротация KEK не требует перешифровать данные, только DEK.
- **Один ключ — одна задача**: подпись сессий, шифрование ПДн, HMAC вебхуков, перец паролей — разные ключи. Компрометация одного не валит всё.
- **Ротация**: план, а не событие. Ключи имеют `kid`; система принимает старый и новый ключ в окне ротации; расписание (например, раз в год) плюс немедленно при подозрении. Для секретов провайдеров — то же.
- **Где не должно быть ключей**: git (включая историю), образы, логи, URL, сообщения об ошибках, клиентский код (всё, что в браузере/приложении, — публично), переменные окружения в `ps`-видимом виде на общем хосте без необходимости.
- **Разделение сред**: ключ dev ≠ staging ≠ prod. Никогда не копировать прод-ключ «для отладки».

## Секреты в разработке и выкладке

- `.env` в `.gitignore`, `.env.example` без значений; pre-commit и CI сканер секретов (gitleaks, trufflehog, GitHub secret scanning с push protection).
- Утечка секрета в git = ротация, даже если коммит удалили: история и форки живут.
- CI: короткоживущие OIDC-токены вместо долгоживущих ключей; секреты не печатать (маскирование не спасает от base64); `pull_request` из форков без секретов (см. `d8`).
- На хосте: файл с правами 600 владельца процесса, systemd `LoadCredential`/`EnvironmentFile`, PM2 `env_file` вне репозитория; не в `ecosystem.config.js`, который коммитится.
- В БД: пароли ролей — сильные, уникальные; строка подключения — секрет.
- Клиент: ключи API третьих сторон не вшиваются в Flutter Web/мобильное приложение; все вызовы через свой бэкенд или с ограниченными публичными ключами (domain-restricted).

## JWT и подписанные токены — ловушки

`alg: none` · подмена RS256→HS256 (публичный ключ как HMAC-секрет) · `kid` с path traversal/SQL · `jku/x5u` на чужой URL · нет проверки `exp/aud/iss` · ключ в репозитории · payload считают зашифрованным (это base64) · бессрочные refresh. Библиотека должна требовать явный список алгоритмов и ключей. Подробно — `d3`.

## TLS

- Серверный: TLS 1.3 (+1.2 с AEAD-шифрами), сертификаты от публичного CA с автообновлением (ACME), OCSP stapling, HSTS; без `SSLv3/TLS1.0/1.1`, без RC4/3DES/CBC-SHA1; проверка — Qualys SSL Labs ≥ A.
- Клиентский (исходящие вызовы): проверка цепочки и hostname включена; pinning только с планом ротации, иначе он ломает вас, а не атакующего.
- Внутри хоста: Postgres через unix-socket или `sslmode=verify-full` по сети; Redis с паролем и TLS, если не локальный сокет.
- Почта: TLS к провайдеру; SPF/DKIM/DMARC для своего домена (см. `d9`).

## Шифрование бэкапов и данных на диске

- Бэкап — `pg_dump` → сжатие → `age -r <public key>` → перенос; приватный ключ только у восстановителя, не на хосте-источнике и не в git. Проверка восстановления по расписанию.
- Шифрование на диске (LUKS/FDE) защищает от кражи носителя, не от взлома процесса. Полевое шифрование чувствительных ПДн (контакты) — защита при утечке дампа; ключ не в той же БД.
- Удаление зашифрованных данных — уничтожение ключа (crypto-shredding), полезно для «права на забвение» в бэкапах.

## Хеширование для приватности

Хеш email/телефона без ключа — не анонимизация: словарь всех телефонов перебирается за минуты. Для псевдонимов — HMAC с секретным ключом; для анонимизации — удаление или агрегация (см. `d7`).

## Пост-квантовая готовность

Для сервиса среднего размера — следить, не внедрять самому: TLS 1.3 с гибридным ML-KEM уже даёт Cloudflare/браузеры; подписи ML-DSA появятся в библиотеках. Важно иметь crypto-agility: версионированные форматы и `kid`.

## Признаки проблемы

`md5(password)` · `AES-CBC` без MAC · один IV на все записи · секрет в `ecosystem.config.js` в git · `Math.random()` для токена · `rejectUnauthorized: false` · бэкап `.sql.gz` без шифра на чужом хосте · прод-ключ в `.env.example` · сравнение токенов через `===`.
