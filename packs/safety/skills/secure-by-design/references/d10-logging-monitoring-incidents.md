# D10. Логи, мониторинг, обработка ошибок и инциденты

> Атаку, которую не заметили, продолжат. Ошибка, которую обработали неправильно, открывает дверь. Инцидент без плана превращается в хаос в три часа ночи.

OWASP A09:2025 Security Logging & Alerting Failures; A10:2025 Mishandling of Exceptional Conditions (новая категория: fail open, неправильная обработка ошибок, логические ошибки при нештатных условиях); CWE-778 (недостаточное логирование), CWE-532 (чувствительное в логах), CWE-209 (ошибка раскрывает лишнее), CWE-755 (неправильная обработка исключений), CWE-636 (fail open), CWE-117 (лог-инъекция). ASVS 5.0: V16 Security Logging and Error Handling. NIST SP 800-61r3 (реагирование на инциденты, 2025), NIST SP 800-92 (логи).

## Что логировать (события безопасности)

| Событие | Поля | Зачем |
|---|---|---|
| Вход: запрос кода, успех, провал, блокировка | user_id или хеш email, IP, UA-хеш, challenge_id, причина | Перебор, credential stuffing, ATO |
| Сессия: создание, ротация, выход, отзыв, step-up | session_id (хеш), user_id, причина | Расследование захвата |
| Отказ в доступе (401/403/404-на-чужой-объект) | user_id, действие, тип и id объекта, correlation_id | IDOR-перебор, эскалация |
| Изменение прав, ролей, членства | кто, кому, что было/стало | Аудит эскалации |
| Чувствительные действия | раскрытие контакта, согласие, экспорт, удаление, смена email | Неотказуемость, расследование |
| Админ-действия | субъект, объект, до/после, причина | Инсайдер |
| Лимиты и отказы | какой лимит, ось, значение | Боты, DoS |
| Ошибки валидации и инъекционные паттерны | эндпоинт, класс ошибки (не сам ввод) | Разведка атакующего |
| Ошибки интеграций и таймауты | провайдер, код, длительность | Деградация, fail-open-риски |
| Изменения конфигурации и деплой | кто, версия, что | Корреляция с инцидентами |
| Доступ к бэкапам и секретам | кто, когда, что | Инсайдер |

Формат: структурированный (JSON), одна запись — одно событие, `timestamp` в UTC с миллисекундами, `event`, `severity`, `correlation_id`, `user_id`, `ip`, `result`, `details` с фиксированной схемой. Correlation id проходит через edge → API → ядро → внешние вызовы и отдаётся клиенту в ошибках.

## Что не логировать никогда

Пароли, коды, токены (в том числе в URL и заголовках `Authorization`, `Cookie`), ключи, полные тела запросов с ПДн, тексты пользователей целиком, номера карт, тексты промптов с ПДн. Маскирование по allow-list полей, а не по regex «на всякий случай». Проверка: тест, который посылает запрос с маркером `SECRET_CANARY` в пароль и ищет его в логах.

## Защита самих логов

- Лог-инъекция: экранирование управляющих символов и переводов строк, лимит длины полей (см. `d1`).
- Неизменяемость: запись только с добавлением, отправка на отдельный хост/сервис (journald → remote, Loki, ELK, облако), права на файлы `640`, ротация с сохранением.
- Срок хранения: события безопасности — 90–365 дней (регуляторика может требовать больше), обычные — 30 дней; ПДн в логах подчиняются `d7`.
- Доступ к логам — отдельная роль с аудитом.
- Часы синхронизированы (NTP), иначе корреляция невозможна.

## Мониторинг и алерты

Алерт — то, на что кто-то реагирует. Минимальный набор:
- Всплеск провалов входа (на аккаунт, на IP, глобально) и срабатываний лимитов.
- Всплеск 403/404 с одного субъекта (перебор id).
- Новая роль админа/модератора, изменение `authorized_keys`, новый sudo, новый пользователь ОС.
- Ошибки 5xx выше порога; рост латентности; падение внешних зависимостей.
- Доступ к бэкапам вне расписания; неудача бэкапа; неудача проверки восстановления.
- Расход у провайдеров (почта, LLM, SMS) выше бюджета — DoS по счёту.
- Истечение сертификата, доменов, ключей.
- Новые критичные CVE в SBOM.
Дашборд — для людей, алерт — для действия, с runbook по каждому: что проверить, что сделать, кого звать. Алерты без runbook отключают через месяц.

## Обработка ошибок (A10:2025)

- **Fail closed** для решений безопасности: сервис проверки недоступен → отказ, а не пропуск; исключение в проверке прав → отказ; неизвестное состояние объекта → отказ.
- **Но ограниченно**: таймаут и circuit breaker, чтобы отказ зависимости не положил всё; деградация для некритичных функций (поиск, ассистент) при сохранении входа и чтения.
- **Единый обработчик ошибок**: любое необработанное исключение → `5xx` с общим текстом и `correlation_id`; стек, SQL, пути, версии — только в лог. Разные классы ошибок — разные коды, но одинаковый формат.
- **Не глотать исключения**: `catch {}` без лога и без решения — дыра (например, ошибка проверки подписи вебхука проглочена → вебхук принят).
- **Нештатные условия**: пустой список, `null` вместо объекта, отрицательные числа, переполнение, часы назад, два одновременных запроса, повторная доставка, частичный сбой транзакции. Каждое — тест.
- **Транзакции**: атомарность многошаговых изменений; откат при ошибке; идемпотентность повторов.
- **Ресурсы при ошибке**: закрыть файлы/соединения, снять блокировки, не оставить «полусозданный» объект без владельца.
- **Debug-режимы** в проде невозможны по конструкции (не флагом, а отсутствием кода).

## План реагирования (NIST 800-61r3)

Напиши заранее, одна страница, лежит в `ops/incident.md`:

1. **Подготовка**: контакты (владелец, devops, юрист, провайдеры), доступы, где логи и бэкапы, шаблоны уведомлений, «тревожный» чат.
2. **Обнаружение и анализ**: кто сообщил, что видно в логах, какие активы затронуты, с какого момента, какие данные; классификация (утечка ПДн / захват аккаунта / компрометация хоста / DoS / supply chain); серьёзность.
3. **Сдерживание**: краткосрочное — отозвать сессии/ключи, заблокировать IP/аккаунт, отключить фичу, выключить интеграцию; сохранить улики (снимок логов, диска) до чистки; долгосрочное — патч, ротация всех затронутых секретов.
4. **Искоренение**: удалить причину (уязвимость, вредоносный пакет, бэкдор), проверить остальные хосты и аккаунты, сменить все пароли/ключи, которые могли утечь.
5. **Восстановление**: из чистого бэкапа или патча, усиленный мониторинг, поэтапное включение.
6. **Уведомления**: пользователи (если риск для них), регулятор (GDPR 72 часа; 152-ФЗ — 24/72 часа Роскомнадзору), партнёры, публичное заявление по необходимости. Честно, без преуменьшения, с тем, что делать человеку.
7. **Постмортем** в течение недели: хронология, корневая причина (не «человек ошибся», а «система позволила»), что сработало, что нет, действия с владельцами и сроками, без обвинений. Обновить модель угроз и чеклисты.

## Раскрытие уязвимостей

`/.well-known/security.txt` (`Contact`, `Expires`, `Policy`, `Preferred-Languages`); политика ответственного раскрытия на сайте: что можно тестировать, чего нельзя, сроки ответа (подтверждение 3 дня, исправление 90 дней), safe harbor. Bug bounty — когда есть кому обрабатывать; до этого — просто благодарности и hall of fame. Входящие сообщения исследователей — в тот же инцидентный процесс.

## Вопросы для брейншторма

1. Какие события безопасности создаёт фича и логируются ли они с нужными полями?
2. Что из данных фичи может попасть в лог случайно (тело запроса, тексты, коды)?
3. По каким событиям сработает алерт и у кого есть runbook?
4. Что делает код при недоступности ядра/БД/провайдера: закрывает или открывает?
5. Какие нештатные условия (пустое, null, повтор, гонка, часы назад) протестированы?
6. Что увидит пользователь при необработанном исключении? А атакующий?
7. Есть ли `catch` без лога и решения?
8. Если завтра утечка: кто первый узнает, где план, кто звонит юристу, готов ли шаблон письма?
9. Как сохранить улики до чистки?
10. Есть ли `security.txt` и куда приходят письма исследователей?

## Признаки проблемы

`console.log(req.body)` · `catch (e) {}` · стек в ответе 500 · «если сервис лимитов недоступен — пропускаем» · логи только на хосте · нет алерта на провалы входа · план реагирования «позвоним Илье» · нет `security.txt` · часы на хосте расходятся на минуты.
