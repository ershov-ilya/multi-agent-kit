# D3. Аутентификация и сессии

> Аутентификация отвечает «кто это?», сессия — «как долго мы этому верим?». Ошибки здесь ведут к захвату аккаунта (ATO), самому дорогому инциденту для продукта с личными данными.

OWASP A07:2025 Authentication Failures; API2:2023 Broken Authentication; CWE-287, CWE-307 (нет лимита попыток), CWE-384 (session fixation), CWE-613 (нет истечения), CWE-640 (слабое восстановление), CWE-798 (hardcoded credentials). ASVS 5.0: V6 Authentication, V7 Session Management, V9 Self-contained Tokens, V10 OAuth/OIDC. NIST SP 800-63B-4 (июль 2025).

## NIST 800-63-4 на практике

Три уровня AAL. **AAL1** — один фактор (пароль, код на email). **AAL2** — два фактора или один фишинг-устойчивый; синхронизируемые passkeys признаны на AAL2. **AAL3** — аппаратный фишинг-устойчивый аутентификатор (device-bound passkey, FIDO2-ключ). Для сервиса с контактами и личными данными цель — AAL2 хотя бы для чувствительных действий.

Правила паролей из 800-63B-4 (нормативный текст — pages.nist.gov/800-63-4):
- Минимум 8 символов при MFA, 15 без MFA; максимум не меньше 64; любые печатные Unicode и пробелы.
- **Запрещены**: требования к составу («буква, цифра, спецсимвол»), периодическая смена без причины, подсказки, секретные вопросы.
- **Обязательно**: проверка по спискам утёкших паролей (Have I Been Pwned k-anonymity API или локальный список), лимит попыток, показывать пароль по желанию, разрешать вставку из менеджера.
- Сила пароля — индикатор, не блокер; главный фильтр — утёкшие и словарные.

## Выбор способа входа

| Способ | Плюсы | Риски | Когда |
|---|---|---|---|
| **Пароль + Argon2id** | Привычно, офлайн-проверка | Переиспользование, фишинг, утечки | Когда нужен вход без доступа к почте/телефону |
| **Одноразовый код на email/мессенджер** | Нет пароля, простой онбординг | Перебор, перехват канала, спам кодами, доступ к ящику = доступ к аккаунту | Пилоты, B2C с низкой ставкой, как второй фактор |
| **Magic link** | Ещё проще | Ссылка в логах прокси/почты, превью мессенджеров «кликают» ссылку, открытие в другом браузере | Как альтернатива коду; токен в URL одноразовый, короткий, с подтверждением в том же браузере |
| **Passkeys (WebAuthn/FIDO2)** | Фишинг-устойчивы, нет секрета на сервере, UX лучше пароля | Поддержка устройств, восстановление при потере | Цель для любого продукта; 2025+ дефолт |
| **TOTP-приложение** | Офлайн, стандарт | Фишится в реальном времени, нужно резервирование | Второй фактор |
| **SMS-код** | Доступен всем | SIM-swap, перехват, стоимость, дроп по стране | Только как восстановление или где нет альтернатив |
| **OAuth/OIDC «войти через»** | Делегируем провайдеру | Зависимость, ошибки реализации, email без верификации у провайдера | Когда аудитория там живёт; проверяй `email_verified` |
| **Telegram Login / бот** | Для Telegram-аудитории | Подпись данных обязательна; `auth_date` свежий | Проверяй HMAC с bot-token, срок `auth_date` ≤ 5 мин |

## Одноразовые коды: канон

- Генерация из CSPRNG; 6 цифр минимум, лучше 8 при большом окне.
- TTL 5–10 минут; одноразовый; новый код инвалидирует старый.
- Хранить **хеш** кода (SHA-256 с солью/HMAC с серверным ключом), не сам код; сравнение за постоянное время.
- Привязка к получателю и к попытке (`challenge_id`): код из письма A не подходит к сессии B.
- Лимит проверок: 3–5 на код, после чего код сгорает; лимит выдачи: на адрес, на IP, на устройство (например, 3 за 10 минут, 10 в сутки); нарастающие задержки.
- Ответ на запрос кода одинаков для существующего и несуществующего адреса (текст, код, время).
- В письме — код и фраза «если это не вы, ничего не делайте»; без ссылки с кодом в URL, если не magic link.
- Ввод кода — в том же браузере/устройстве, где запрошен (`challenge_id` в httpOnly cookie), это режет фишинг «введи код, который тебе пришёл».
- Логировать события (запрос, успех, провал, блокировка) без значения кода.

## Хранение паролей

**Argon2id** (память 19–64 МиБ, итерации 2–3, параллелизм 1; OWASP: m=19456, t=2, p=1 минимум) → **scrypt** → **bcrypt** (cost 10–12, помни лимит 72 байта и обрезание) → PBKDF2-HMAC-SHA256 (600 000+ итераций, только где нет альтернативы, FIPS). Соль уникальная на пароль, библиотека генерирует сама. Опционально «перец» — серверный ключ вне БД, через HMAC до хеша. Никогда: MD5, SHA-1, SHA-256 без растяжения, свой алгоритм, обратимое шифрование. Миграция: перехешировать при следующем входе, старые хеши обернуть (`argon2(bcrypt(p))`).

## Брутфорс, перебор, перечисление

- Лимиты по трём осям: аккаунт, IP, глобально. Экспоненциальная задержка, затем временная блокировка аккаунта с уведомлением владельца; не блокируй навсегда (DoS против жертвы).
- Credential stuffing: проверка по утёкшим, device fingerprint, капча после N провалов, уведомление «вход с нового устройства».
- **Перечисление аккаунтов** (CWE-204): одинаковые ответы на вход/регистрацию/восстановление; одинаковое время (хешируй фиктивный пароль при отсутствии пользователя); регистрация с занятым email — «письмо отправлено» и письмо «у вас уже есть аккаунт».
- Password spraying: один пароль на много аккаунтов — ловится глобальным лимитом и аналитикой.

## Восстановление доступа (CWE-640)

Самое слабое звено. Токен сброса: 128+ бит из CSPRNG, хеш в БД, TTL ≤ 1 час, одноразовый, инвалидируется при новом запросе и при смене пароля; ссылка только по HTTPS, `Referrer-Policy: no-referrer` на странице; после сброса — завершить все сессии и уведомить. Не использовать секретные вопросы. Восстановление через поддержку — процедура с верификацией и журналом. Для passkeys — резервный фактор заранее (второй passkey, recovery-коды).

## Сессии

| Вопрос | Канон |
|---|---|
| Идентификатор | ≥128 бит из CSPRNG, непредсказуемый, без смысла внутри |
| Где хранить состояние | На сервере (БД/Redis): легко отозвать, видно активные. Это дефолт |
| Передача | Cookie `__Host-sid`, `Secure; HttpOnly; SameSite=Lax; Path=/` |
| Ротация | Новый id при входе, повышении привилегий, смене пароля (против session fixation, CWE-384) |
| Срок | Idle-таймаут (например, 30 дней для B2C, 30 минут для админки) и абсолютный (например, 90 дней); чувствительные действия — повторная аутентификация (step-up) |
| Выход | Удалить на сервере, не только cookie; «выйти везде» |
| Привязка | Опционально к устройству/UA; при смене — уведомление, не блок |
| Видимость | Список активных сессий пользователю с отзывом |

## JWT и самодостаточные токены (ASVS V9)

JWT уместен для короткоживущих access-токенов между сервисами или в OAuth. Как сессия пользователя он создаёт проблему отзыва. Если используешь:
- Алгоритм фиксирован на сервере (`EdDSA`/`ES256`/`RS256` для асимметрии, `HS256` только между своими сервисами с секретом ≥256 бит); **`alg: none` и подмена RS→HS** — классика, библиотека должна принимать только явный allow-list.
- `kid`/`jku`/`x5u` — только из allow-list ключей, не из URL в токене.
- Проверять `exp`, `nbf`, `iss`, `aud`, `iat`; срок access-токена 5–15 минут.
- Refresh-токен — непрозрачный, в httpOnly cookie, одноразовый с ротацией и обнаружением повторного использования (отозвать всю семью).
- Отзыв: короткий `exp` + denylist по `jti` или серверная проверка версии сессии.
- Не класть ПДн и роли, которым верят без перепроверки, в payload: он только base64.
- Хранение в браузере: `localStorage` читается любым XSS. Лучше httpOnly cookie + CSRF-защита, либо память + refresh в cookie (BFF-паттерн).

## OAuth 2.1 / OIDC (ASVS V10)

- Только **Authorization Code + PKCE** для всех клиентов; implicit и password grant мертвы.
- `state` — CSRF-защита, `nonce` — привязка id_token к сессии; оба непредсказуемые и проверяемые.
- `redirect_uri` — точное сравнение со списком, без wildcard и без открытых редиректов на нём.
- Проверять `iss`, `aud`, подпись id_token, `email_verified`; не связывать аккаунт по email без верификации (account takeover через провайдера, где email не подтверждён).
- Scope минимальный; токены провайдера хранить зашифрованными, если вообще нужны.
- Mix-up attack при нескольких провайдерах: `iss` в ответе авторизации или раздельные redirect_uri.
- Для своих API: короткие access-токены, `aud` под каждый ресурс, DPoP/mTLS для привязки к клиенту, если ставка высокая.

## MFA и step-up

- Второй фактор по умолчанию для админов и при чувствительных действиях (смена email/пароля, раскрытие контактов, экспорт данных, платежи).
- Фишинг-устойчивость: passkeys/FIDO2 > TOTP > push (с number matching, против push-bombing) > SMS.
- Recovery-коды одноразовые, хешированные, показываются один раз.
- Step-up: запрос повторной аутентификации, если последняя была > N минут назад, для действия из списка.
- «Запомнить устройство» — отдельная cookie с собственным сроком, отзываемая.

## Service-to-service

Не «аутентификация пользователя», но те же правила: секреты не в коде, короткоживущие токены (OIDC из CI, workload identity), mTLS внутри, allow-list IP как дополнительный, не единственный контроль, ротация.

## Вопросы для брейншторма

1. Какой AAL нужен каждому действию в фиче? Где step-up?
2. Что произойдёт при перехвате канала доставки кода (почта, Telegram)? Это принято?
3. Лимиты на код: попыток, выдач, окно, оси (аккаунт/IP/устройство)? Как тестируются?
4. Раскрывают ли ответы или время существование аккаунта?
5. Где хранится сессия, как отзывается, какие сроки, ротируется ли при входе?
6. Если JWT: кто фиксирует `alg`, где `aud`, как отзывается, где лежит в браузере?
7. Как восстанавливается доступ? Что видит поддержка и как верифицирует?
8. Как пользователь узнаёт о входе с нового устройства и что может сделать?
9. Если OAuth: PKCE, `state`, `nonce`, точный `redirect_uri`, `email_verified`?
10. Какие секреты (ключи подписи, перец) нужны и как ротируются?

## Признаки проблемы

Код входа без лимита попыток · код хранится в открытом виде · «пользователь не найден» в ответе · session id не меняется при входе · JWT в `localStorage` · `alg` берётся из токена · refresh-токен бессрочный · восстановление через «девичью фамилию» · bcrypt с cost 4 · одна учётка сервиса на всё.
