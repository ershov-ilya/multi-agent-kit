# Чеклисты

Готовые списки для шести ситуаций. Каждый пункт помечен доменом, чтобы при «нет» открыть нужный файл. Чеклист — не замена модели угроз, а страховка от забытого.

## 1. RFC / брейншторм новой фичи

**Рамка (D0)**
- [ ] Назван актив и ущерб от его компрометации словами.
- [ ] Названы 2–4 профиля противника.
- [ ] Нарисован поток данных с границами доверия.
- [ ] По каждой границе пройден STRIDE; для ПДн — LINDDUN.
- [ ] Решение «можно ли» принимается на сервере в одном месте.

**Ввод и вывод (D1, D2)**
- [ ] Каждый вход описан схемой с запретом лишних полей, лимитами длины и диапазонов.
- [ ] Перечислены все стоки (SQL, FS, shell, шаблон, regex, лог, email, LLM) и способ отделения данных от команд.
- [ ] Пользовательские строки попадают в HTML только через автоэкранирование/санитизацию.
- [ ] Файлы: тип по содержимому, своё имя, отдельный origin отдачи.

**Доступ (D3, D4)**
- [ ] Для каждого действия определён требуемый уровень аутентификации и step-up.
- [ ] Для каждого эндпоинта: проверка функции, объекта, полей; `community_id`/`owner_id` из сессии.
- [ ] Поля, появляющиеся после события (согласие, оплата), отдаются только по решению ядра.
- [ ] Статусные поля меняются только через выделенные переходы.
- [ ] Тест «чужой не видит» запланирован на каждый объектный эндпоинт.

**API и интеграции (D5)**
- [ ] Лимиты: размер, частота, стоимость, параллелизм, таймауты — по осям.
- [ ] Пагинация с максимумом.
- [ ] Нет серверных запросов по URL из ввода; если есть — allow-list и запрет приватных сетей.
- [ ] Вебхуки: подпись, replay-окно, идемпотентность.
- [ ] Ответы чужих API валидируются как ввод; fail closed для решений доступа.

**Криптография и данные (D6, D7)**
- [ ] Новые секреты: где лежат, кто ротирует, что при утечке.
- [ ] Нет самодельной криптографии; выбраны AEAD/Argon2id/HMAC/Ed25519 из таблицы.
- [ ] Таблица «поле → цель → основание → хранилище → срок → удаление → третьи лица» заполнена.
- [ ] Что из данных попадает в логи, аналитику, трекер ошибок, LLM — перечислено и минимизировано.
- [ ] Агрегаты и ответы не раскрывают наличие конкретного человека.

**Платформа (D8, D9)**
- [ ] Новые зависимости проверены (автор, возраст, скрипты, альтернатива).
- [ ] Новые процессы/порты/роли БД — под минимальными правами.
- [ ] Лимиты на edge для новых путей.

**Операции (D10)**
- [ ] Перечислены события безопасности фичи и поля логов.
- [ ] Определены алерты и runbook, если фича создаёт новый риск.
- [ ] Поведение при недоступности зависимостей: закрыто или деградация.
- [ ] Нештатные условия (пустое, null, повтор, гонка) в тестах.

**Логика и люди (D11)**
- [ ] Диаграмма состояний и таблица переходов с актором.
- [ ] Ответ на «два одновременных запроса» и «повтор через 10 секунд».
- [ ] Что ценно для бота и какая ступень антиавтоматизации.
- [ ] Как честный пользователь может навредить другому и что тот сделает (жалоба, блок).

**ИИ (D12), если есть модель**
- [ ] Что модель видит и что не имеет права вернуть.
- [ ] Инструменты: список, побочные эффекты, подтверждения; «смертельная тройка» разорвана.
- [ ] Вывод модели валидируется по схеме перед любым использованием.
- [ ] Изоляция по пользователю и сообществу до поиска.
- [ ] Лимиты расхода и набор атак в тестах.

**Процесс (D13)**
- [ ] Раздел «Безопасность» в RFC написан по шаблону.
- [ ] Остаточные риски записаны с владельцем и датой пересмотра.

## 2. Дизайн-ревью RFC

- [ ] Есть ли раздел «Безопасность», и отвечает ли он на «актив, противник, границы, угрозы, контроли, данные, остаточное»?
- [ ] Где именно в архитектуре принимается решение о доступе? Одно ли это место?
- [ ] Что получит запрос без токена, с чужим id, с лишним полем, при упавшей зависимости?
- [ ] Какие общие механизмы (кэш, индекс, очередь, эмбеддинги) не разделены по арендатору?
- [ ] Какая привилегия выдана «на всякий случай»?
- [ ] Какой секрет при утечке открывает всё?
- [ ] Что из данных можно не собирать?
- [ ] Какие действия необратимы и требуют двух условий?
- [ ] Какой контроль не имеет теста?
- [ ] Что в RFC противоречит принципам: deny by default, least privilege, fail closed, параметризация, решение на сервере?
Вердикт: «строить» / «строить с условиями: …» / «переработать: …».

## 3. Код-ревью

Для каждого изменённого файла:
- [ ] **Ввод** (D1): новые входы описаны схемой; нет конкатенации в SQL/shell/шаблон/путь; regex без вложенных квантификаторов; `yaml.load`/XML с DTD/десериализация объектов отсутствуют.
- [ ] **Вывод** (D2): нет `innerHTML`/`dangerouslySetInnerHTML`/raw HTML; редиректы по allow-list; новые заголовки/cookie с флагами.
- [ ] **Аутентификация** (D3): коды/токены из CSPRNG, хешированы, с TTL и лимитом; сессия ротируется; JWT с фиксированным `alg`.
- [ ] **Авторизация** (D4): загрузка объекта с фильтром по субъекту; роль из БД/сессии; allow-list полей на запись; DTO на чтение; тест «чужой не видит» добавлен.
- [ ] **API** (D5): лимиты и пагинация; исходящие запросы с таймаутом, проверкой TLS и allow-list хостов; вебхуки с подписью.
- [ ] **Крипто/секреты** (D6): нет `md5/sha1` для секретов, нет `Math.random`, нет ручного AES-CBC; секреты не в коде и не в тестах; сравнение за постоянное время.
- [ ] **Данные** (D7): новые поля в инвентаре; ПДн не в логах; срок и удаление реализованы.
- [ ] **Зависимости** (D8): lock-дифф проверен; новые пакеты обоснованы; CI-экшены по SHA.
- [ ] **Инфраструктура** (D9): конфиги без секретов; новые порты/роли минимальны; миграции не расширяют гранты.
- [ ] **Ошибки и логи** (D10): нет `catch {}`; ошибки в единый обработчик; события безопасности логируются; `console.log(req.body)` отсутствует.
- [ ] **Логика** (D11): переходы состояний атомарны (`UPDATE … WHERE status`); уникальные индексы; идемпотентность; числа с клиента проверены.
- [ ] **LLM** (D12): чужой текст передаётся как данные; вывод валидируется; инструменты узкие.
Находка оформляется: файл:строка · CWE · сценарий в одну фразу · исправление · серьёзность.

## 4. Перед релизом

- [ ] Все пункты DoD фичи закрыты (D13).
- [ ] Лимиты включены в проде и проверены запросом (D5, D9).
- [ ] Заголовки безопасности и TLS проверены сканером (D2, D9).
- [ ] Секреты прода отличаются от staging; `.env` не в образе и не в git (D6).
- [ ] `NODE_ENV`/debug/introspection/playground недоступны в проде (D9).
- [ ] SCA и secret scanning зелёные; критичных CVE нет (D8).
- [ ] Миграции обратимы; бэкап снят до выкладки; восстановление проверялось в этом квартале (D7, D9).
- [ ] Алерты на провалы входа, 5xx, расход провайдеров настроены (D10).
- [ ] Тесты авторизации и валидации проходят в CI (D4, D1).
- [ ] Инвентарь (эндпоинты, секреты, данные) обновлён (D13).
- [ ] Для LLM-изменений: набор атак прогнан (D12).
- [ ] План отката за минуту известен (D9).

## 5. После инцидента

- [ ] Улики сохранены до чистки (логи, снимки).
- [ ] Затронутые сессии отозваны, секреты ротированы, уязвимость закрыта.
- [ ] Определено: чьи данные, какие, с какого момента.
- [ ] Уведомления: пользователи, регулятор (сроки!), партнёры.
- [ ] Постмортем: хронология, корневая причина как свойство системы, действия с владельцами.
- [ ] Модель угроз, чеклисты и тесты обновлены, чтобы класс ошибки больше не повторился.
- [ ] Проверено, не затронуты ли соседние системы тем же вектором.

## 6. Аудит существующего сервиса (первый проход за день)

1. **Поверхность**: внешний скан портов, список доменов и путей, OpenAPI против реальных роутов, `security.txt`, заголовки, TLS (D9, D2, D5).
2. **Вход**: лимиты на коды/пароли, перечисление аккаунтов, флаги cookie, сроки сессий, восстановление (D3).
3. **Доступ**: взять три объектных эндпоинта, подставить чужой id из того же и другого сообщества (D4).
4. **Ввод**: grep по `innerHTML|dangerouslySetInnerHTML|exec\(|eval\(|\$\{.*\}.*(select|insert|update|delete)|new RegExp\(|yaml\.load` (D1, D2).
5. **Секреты**: gitleaks по всей истории; где лежат `.env`; права файлов; ротировались ли (D6).
6. **Данные**: какие ПДн есть, где, срок, удаление, что в логах и у третьих лиц (D7).
7. **Зависимости**: SCA, lock-файл, `postinstall`, экшены по тегу (D8).
8. **Хост**: пользователи процессов, `pg_hba`, открытые порты, обновления, бэкап и его шифрование (D9).
9. **Логи и реакция**: что логируется, что алертит, где план инцидента (D10).
10. **Логика**: гонки на согласиях/оплате, лимиты на ценные потоки, жалобы и блокировки (D11).
11. **LLM**: что видит модель, инструменты, изоляция, лимиты (D12).
Выход: таблица рисков (В×У), топ-5 «закрыть на этой неделе», план на квартал.
