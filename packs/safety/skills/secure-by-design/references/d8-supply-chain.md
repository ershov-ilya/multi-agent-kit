# D8. Цепочка поставки и сборка

> Зависимость — чужой код, который выполняется в вашем процессе с вашими правами и секретами. Сборка — место, где этот код и ваш превращаются в то, что едет в прод. Атаки на цепочку поставки масштабируются: один пакет — тысячи жертв.

OWASP A03:2025 Software Supply Chain Failures (новая категория, расширение «Vulnerable and Outdated Components»), A08:2025 Software or Data Integrity Failures; CWE-1395 (зависимость от уязвимого компонента), CWE-829 (функциональность из ненадёжной сферы), CWE-494 (загрузка кода без проверки целостности), CWE-506. Стандарты: SLSA (v1.0), NIST SSDF (SP 800-218), OpenSSF Scorecard, CycloneDX/SPDX (SBOM), Sigstore.

## Карта атак

| Вектор | Как выглядит | Пример из практики |
|---|---|---|
| **Уязвимость в зависимости** | Известная CVE в транзитивном пакете | Log4Shell (2021), уязвимости в `lodash`, `axios`, `fast-xml-parser` |
| **Вредоносный пакет** | Пакет с `postinstall`, крадущий `.env`, токены npm, ключи SSH | `event-stream` (2018), `ua-parser-js` (2021), волна 2023–2025 в npm/PyPI |
| **Typosquatting** | `lodahs`, `requets`, `crossenv` | Постоянно |
| **Dependency confusion** | Внутренний пакет `@company/util` перекрыт публичным с большей версией | Birsan, 2021 |
| **Slopsquatting** | ИИ-ассистент выдумывает имя пакета; атакующий регистрирует его | 2024–2025, исследования показывают до 20 % галлюцинированных имён в сгенерированном коде |
| **Захват мейнтейнера** | Украденный токен или переданный проект | `xz-utils` (2024), `polyfill.io` (2024), `tj-actions/changed-files` (2025) |
| **Компрометация CI** | Секреты через `pull_request_target`, инъекция в `run:` через заголовок PR, незапиненный экшен | Codecov (2021), GitHub Actions-инциденты 2024–2025 |
| **Подмена артефакта** | Образ/бинарник подменён между сборкой и деплоем | SolarWinds (2020) |
| **Скрипт установки из сети** | `curl … \| sh`, `pip install` из git без хеша | Классика |
| **Чужой JS на странице** | CDN-скрипт изменился | `polyfill.io`, Magecart |
| **Базовый образ** | Устаревший `node:18` с CVE в ОС | Постоянно |
| **Модель/датасет** | Веса с pickle-нагрузкой, отравленный датасет | См. `d12` |

## Контроли по слоям

### Зависимости
- **Lock-файл в git** (`package-lock.json`, `Cargo.lock`, `pubspec.lock`), установка только из него (`npm ci`, `cargo --locked`), ревью изменений lock-файла как кода.
- **Пиннинг** точных версий для прямых зависимостей там, где обновление нужно осознанно; диапазоны — только с lock-файлом.
- **Минимум зависимостей.** Перед добавлением: кто автор, сколько мейнтейнеров, когда последний релиз, сколько транзитивных, есть ли `postinstall`, OpenSSF Scorecard, сколько строк вы бы написали сами. Пакет на 10 строк — пиши сам.
- **`ignore-scripts`** в `.npmrc` для CI и по умолчанию; включать скрипты точечно (`node-gyp`-пакеты) через allow-list.
- **Cooldown**: не ставить версию младше N дней (npm `--before`, `minimum-release-age`, Renovate `minimumReleaseAge`). Большинство вредоносных релизов снимают за 24–72 часа.
- **Scoped-пакеты и приватный реестр** с запретом публичного fallback для внутренних имён; зарезервировать имена своих пакетов публично (`@your-org/*`).
- **Проверка имени**: пакет, предложенный ИИ, проверяется на существование, возраст, скачивания и автора до установки.
- **Rust**: `cargo audit`, `cargo deny` (лицензии, дубликаты, источники), `cargo vet`/`cargo crev` для ревью, `[dependencies]` без `git =` на ветку.
- **Dart/Flutter**: `pubspec.lock`, `dart pub outdated`, проверка pub.dev-верификации издателя.

### Сканирование
- **SCA** в каждом PR и по расписанию: `npm audit` (шумный, но базовый), OSV-Scanner, Trivy, Snyk/Dependabot/Renovate. Правило: критичные блокируют мерж, остальное — тикет со сроком.
- **Автообновления** через Renovate/Dependabot с группировкой и cooldown, обязательным CI и ревью lock-диффа.
- **SBOM** (CycloneDX или SPDX) генерируется на сборке и хранится рядом с артефактом: при новой CVE отвечаем «затронуты ли мы» за минуту, а не за день.
- **Secret scanning** на push и в CI (`gitleaks`, GitHub push protection).

### CI/CD
- **Экшены по SHA**, не по тегу: `uses: actions/checkout@<40-hex>` (тег переписывается, SHA — нет). Dependabot обновляет SHA.
- **`pull_request_target`** и `workflow_run` — запускают код с секретами для чужого PR. Не использовать с checkout PR-кода; если нужно — без секретов и с явным разделением.
- **Инъекция через контекст**: `run: echo ${{ github.event.pull_request.title }}` — заголовок PR выполняется в shell. Передавать через `env:` и кавычки.
- **Минимальные `permissions:`** на workflow (`contents: read` по умолчанию), `GITHUB_TOKEN` без write, где не нужно.
- **OIDC** для доступа к облаку/реестру вместо долгоживущих ключей в секретах.
- **Защита ветки**: обязательное ревью, статус-чеки, запрет force-push в `main`, подписанные коммиты (`gpg`/`ssh` signing) хотя бы для релизов.
- **Изоляция раннеров**: эфемерные, без доступа к проду; деплой — отдельный job с approval и отдельными секретами.
- **Логи CI** — не печатать секреты и env; артефакты — с ограниченным сроком.

### Артефакты и выкладка
- **Воспроизводимая сборка** или хотя бы детерминированные версии инструментов (`.nvmrc`, `rust-toolchain.toml`).
- **Подпись и provenance**: Sigstore/cosign для образов и релизов, `npm publish --provenance`, SLSA-аттестации; проверка на стороне деплоя.
- **Образы**: минимальная база (`distroless`, `alpine`, `-slim`), пиннинг по digest (`node:22-bookworm-slim@sha256:…`), многостадийная сборка, сканирование Trivy/Grype, не root внутри, `.dockerignore` с `.env` и `.git`.
- **Деплой с хоста**: `git pull` из доверенного remote по SSH-ключу с read-only deploy key, проверка тега/подписи, `npm ci --ignore-scripts`, сборка под отдельным пользователем.
- **Чужой JS/CSS на странице**: self-host или SRI + CSP; никакого «подключим аналитику скриптом с чужого домена без хеша».

## Уровни SLSA (ориентир)

| Уровень | Требование | Что даёт |
|---|---|---|
| L0 | Ничего | — |
| L1 | Provenance генерируется (кто, что, из чего собрал) | Инвентарь |
| L2 | Сборка на хостинг-платформе, provenance подписан | Защита от подмены после сборки |
| L3 | Изолированная, не изменяемая сборка; секреты недоступны шагам | Защита от компрометации раннера |

Для пилота: L1–L2 через GitHub Actions с `--provenance` и подписью релизов — достижимо за день.

## Код от ИИ-ассистентов

Код, который предложил ассистент, — зависимость из недоверенного источника: ревью как чужой PR; проверка каждого имени пакета; запрет копирования секретов и прод-конфигов в промпт; правило «ассистент не выполняет `npm install` без человека» в настройках агента; сгенерированный код проходит те же SAST/SCA.

## Вопросы для брейншторма

1. Какие новые зависимости добавляет фича? Для каждой: автор, возраст, скрипты установки, альтернатива «написать самим»?
2. Включён ли `ignore-scripts`, cooldown, lock-файл в CI?
3. Что в CI запускается на чужой PR и с какими секретами? Пиннинг экшенов по SHA?
4. Есть ли SBOM, и сможем ли за минуту ответить «затронуты ли мы CVE-X»?
5. Как артефакт попадает на прод и как проверяется, что это тот артефакт?
6. Какой базовый образ, когда обновлялся, кто внутри root?
7. Какие чужие скрипты грузит клиент?
8. Что из прод-секретов видно раннеру CI?
9. Если мейнтейнер ключевого пакета уйдёт или будет взломан, как узнаем?
10. Проверяются ли имена пакетов, предложенных ИИ?

## Признаки проблемы

`uses: some/action@v3` · `pull_request_target` с checkout · lock-файла нет в git · `postinstall` разрешён везде · `curl | sh` в Dockerfile · `FROM node:latest` · `<script src="https://cdn.…/lib.js">` без SRI · 400 транзитивных пакетов ради одной утилиты · PR от Dependabot мержатся без CI.
