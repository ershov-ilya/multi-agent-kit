# D5. API и интеграции

> API вызывают не только из вашего клиента. Каждый эндпоинт — публичный контракт, по которому будут ходить curl, боты и чужие интеграции. Проектируй так, будто клиента нет.

OWASP API Security Top 10:2023; A01:2025 (SSRF теперь внутри Broken Access Control); CWE-918 SSRF, CWE-770 Allocation without limits (#25 в Top 25:2025), CWE-200. ASVS 5.0: V4 API and Web Service.

## Лимиты (API4)

Осей несколько, и нужны все:
- **Размер**: тело (`bodyLimit`), заголовки, URL, число полей, глубина JSON, размер файла, длина строк.
- **Частота**: на IP, на пользователя, на токен, на эндпоинт, глобально; `429` с `Retry-After`; разные лимиты для дешёвых и дорогих методов.
- **Стоимость**: пагинация обязательна с максимальным `limit`; запрет `limit=100000`; для поиска и агрегаций — таймаут запроса к БД (`statement_timeout`), лимит сложности GraphQL; для LLM — лимит токенов и вызовов (см. `d12`).
- **Параллелизм**: число одновременных соединений/SSE на пользователя; очереди с backpressure.
- **Время**: таймауты на все исходящие вызовы и на обработку запроса.
- Лимит — не только защита, но и бизнес-правило: «10 запросов на знакомство в сутки» защищает других пользователей от спама.

## SSRF (API7, CWE-918)

Сервер скачивает «аватар по URL», проверяет вебхук, рендерит превью ссылки, прокси до внешнего API — и ходит в `http://169.254.169.254/` (метаданные облака), `http://localhost:5432`, внутренний админ-интерфейс.

Контроль: allow-list хостов/доменов, если возможно; иначе — резолвить DNS, отклонять приватные/loopback/link-local диапазоны (IPv4 и IPv6, включая `::ffff:127.0.0.1`, decimal/octal записи), запрещать редиректы или проверять каждый hop, только `http(s)`, таймаут и лимит размера ответа, отдельная сетевая зона/egress-прокси для исходящих, не возвращать тело ответа пользователю целиком. DNS rebinding: резолвить один раз и соединяться по IP (`lookup`-хук).

## Вебхуки: принимаем

- **Подпись**: HMAC-SHA256 тела с общим секретом, заголовок `X-Signature`, сравнение за постоянное время; у провайдеров — их схема (Stripe `t=…,v1=…`, GitHub `X-Hub-Signature-256`, Telegram `secret_token`).
- **Replay**: timestamp в подписи, окно ±5 минут, идемпотентность по `event_id` (таблица обработанных).
- **Обработка**: валидировать тело как ввод, не доверять полям вроде `amount` — перепроверять через API провайдера, если ставка высокая.
- **Ответ**: быстро `200`, обработка в очереди; ошибка обработки не должна раскрывать внутренности.
- **Эндпоинт**: непредсказуемый путь не заменяет подпись; allow-list IP провайдера — дополнение.

## Вебхуки: отправляем

Это SSRF-поверхность (URL задаёт пользователь) — те же правила. Подписывать своим ключом, документировать проверку, ротация секрета, retry с backoff, не слать ПДн, которых получателю не нужно.

## Идемпотентность и повторы

`Idempotency-Key` для POST с побочным эффектом (платёж, создание оффера): ключ от клиента, сервер хранит результат на 24 часа и возвращает его при повторе; ключ привязан к пользователю. Retry без идемпотентности = дубли и двойные списания.

## Потребление чужих API (API10)

Ответ чужого сервиса — ввод: схема, лимит размера, таймаут, проверка TLS (не отключать `rejectUnauthorized`), не прокидывать его поля в SQL/HTML без обработки, не следовать редиректам вслепую. Секреты провайдера — в хранилище секретов, минимальный scope, ротация. Деградация при недоступности — fail closed для решений о доступе, graceful для некритичного. Circuit breaker.

## Идентификаторы, ошибки, версии

- id наружу — UUID/ULID; внутренние последовательные — не светить.
- Ошибка — единый формат `{code, message, correlation_id}`; `404` и `403` на чужой объект неразличимы; без стеков, SQL, путей, версий библиотек; `5xx` — общий текст, детали в логе по `correlation_id`.
- Версии: старые версии имеют дату смерти; тестовые/отладочные роуты не существуют в проде (не «скрыты», а не зарегистрированы); OpenAPI генерируется из кода, чтобы инвентарь был честным (API9).
- Методы: `GET` без побочных эффектов; `HEAD/OPTIONS` не раскрывают лишнего; неизвестный метод → 405.

## GraphQL

Авторизация на уровне резолвера и поля; лимит глубины, сложности и количества алиасов; batching-лимит; introspection и playground выключены в проде; persisted queries для публичных клиентов; ошибки без путей резолверов.

## gRPC / внутренние API

mTLS или токены между сервисами; deadline на каждый вызов; лимит размера сообщений; валидация protobuf-полей (protobuf не валидирует смысл); не доверять `metadata` без проверки.

## Telegram-боты и relay

Запросы к Bot API идут только с серверной стороны; токен бота — секрет вне git; при вебхуке — `secret_token` и проверка заголовка; при long polling — один потребитель; входящие сообщения — ввод (валидация, лимиты, запрет команд из текста для LLM); привязка Telegram-аккаунта к пользователю — через одноразовый код/deep-link с TTL, а не по `username`; relay наружу — узкий allow-list методов, аутентификация вызывающего, лимиты.

## Вопросы для брейншторма

1. Что произойдёт, если вызвать каждый эндпоинт фичи из curl без клиента: с чужим id, с лишними полями, с `limit=10⁶`, 1000 раз в минуту?
2. Какие поля в ответе нужны именно этому экрану? Что лишнее?
3. Где сервер ходит по URL, который хоть частично задаёт пользователь или внешний сервис?
4. Как проверяется подпись и replay каждого входящего вебхука?
5. Есть ли идемпотентность у операций с побочным эффектом?
6. Какие исходящие вызовы без таймаута или без проверки TLS?
7. Что делаем при недоступности провайдера (почта, LLM, Telegram): fail closed или open?
8. Какие эндпоинты существуют, но не в документации? Какие версии живы?
9. Что раскрывает формат ошибок?
10. Какой лимит на создание ценных сущностей (офферы, инвайты, коды) и на чью ось?

## Признаки проблемы

Пагинация без максимума · `fetch(userUrl)` без проверки хоста · вебхук без подписи · `rejectUnauthorized: false` · стек в ответе 500 · `GET /debug` в проде · поле `phone` в ответе с флагом `hidden` · ответ чужого API прямо в SQL.
