# H6. Уведомления и возвращение

> Уведомление — это запрос внимания в чужое время. Люди дают разрешение, когда уже увидели ценность и понимают, о чём их будут беспокоить, и отзывают при первом же шуме. Канал выбирает пользователь; продукт лишь предлагает.

Источники: Airship Push Benchmarks 2025–2026 (медиана opt-in: Android ≈ 53 %, iOS ≈ 49 %; Android падает после Android 13), Batch 2025 (Android ≈ 67 %, iOS ≈ 56 %), Pushwoosh 2025 (CTR push 2–10 % по вертикалям), Localytics/Braze (отключают при > 5 в неделю для большинства категорий), NN/g notification research, Mediascope 2026 (мессенджеры в России), Gmail/Yahoo sender requirements 2024 (one-click unsubscribe), ЗоЗПП и 38-ФЗ (см. `legal`).

## Привычки

| Привычка | Что наблюдаем | Что это значит | Типичная ошибка |
|---|---|---|---|
| **Отказывают при первом запуске** | Системный запрос на старте → отказ, и второго шанса в iOS нет без настроек | Предзапрос своим экраном в момент ценности; системный — после «да» | Запрос при первом открытии |
| **Соглашаются, когда ждут событие** | «Сообщить, когда ответят?» → да | Привязать запрос к ожиданию: после отправки запроса, бронирования, заказа | Запрос «для новостей» |
| **Отключают при шуме** | Маркетинг в push, частота > нескольких в неделю, ночные → отключение всего | Транзакционные и ожидаемые — в push; маркетинг — отдельная категория, выключенная по умолчанию | Акции в том же канале, что ответы |
| **Хотят гранулярность** | Настройки по типам событий и каналам; «только важное» | Экран настроек: тип события × канал; разумные дефолты | Один переключатель «уведомления» |
| **Канал — тот, где живут** | В России — Telegram/Max/WhatsApp, затем push, email для документов; SMS — для кодов | Предложить выбор канала при первом событии; помнить выбор | Только email |
| **Email читают по делу, не по рассылке** | Транзакционные открывают (40–70 %), маркетинговые — 15–25 %; дайджест лучше потока | Письма по событию; дайджест раз в неделю вместо ежедневных | Ежедневные письма «что нового» |
| **Тихие часы** | Уведомления ночью и ранним утром раздражают и отключаются | Отправлять в активное окно пользователя (по его часовому поясу и истории), иначе откладывать | Отправка по серверному времени |
| **Бейдж как долг** | Красная цифра тревожит; если не сбрасывается — перестают замечать | Бейдж только для требующего действия; сбрасывается при просмотре | Бейдж на маркетинг |
| **Уведомление без контекста не открывают** | «У вас новое событие» → игнор; «Анна ответила на ваш запрос о попутчике» → открывают | Конкретика: кто, что, про что; deep link на объект | Общие формулировки |
| **Ждут, что уведомление ведёт к объекту** | Открыли — попали на главную → раздражение | Deep link на карточку с «назад» в раздел | Ссылка на главную |
| **Группировка** | Пять уведомлений об одном — спам; одно «3 новых ответа» — нормально | Агрегация, лимит в час, обновление вместо нового | Уведомление на каждое событие |
| **Отписка в один клик** | Ищут «отписаться» в письме; если нет — спам-жалоба | List-Unsubscribe, ссылка в каждом письме, настройка в профиле | Отписка через поддержку |
| **Возвращаются по причине, не по напоминанию** | «Мы скучаем» — не работает; «появились 2 новых человека по вашему запросу» — работает | Триггер возврата — реальное событие или изменение | Рассылка «давно не заходили» |
| **Окно возврата** | Если нет причины вернуться в первые дни, вероятность падает быстро; после 30 дней — почти ноль | Запланировать события для возврата: ответ, новые совпадения, итог недели | Тишина после онбординга |
| **Боты в мессенджере как канал** | Принимают уведомления от бота, если сами привязали; отписываются блокировкой бота | Привязка по действию пользователя; команды «стоп/настроить»; не чаще, чем просили | Бот пишет первым без привязки |

## Лучшие практики

- **Предзапрос**: свой экран «Сообщать, когда ответят?» → «Да» / «Позже»; системный диалог только после «Да». Повторный предзапрос — не раньше следующего ожидаемого события.
- **Классы уведомлений**: транзакционные (ответ, статус) — всегда; ожидаемые (новые совпадения) — по умолчанию включены с частотой; маркетинг — выключен по умолчанию, отдельное согласие (см. `legal` L6).
- **Выбор канала** при первом событии: push / Telegram / email; помнить; показывать, куда придёт.
- **Частота**: лимит по классу (например, транзакционные без лимита, ожидаемые ≤ 1 в день, дайджест ≤ 1 в неделю); агрегация за окно.
- **Тихие часы** по часовому поясу пользователя (23:00–8:00 по умолчанию), с настройкой.
- **Текст**: кто + что + про что, ≤ 2 строк; глагол действия; без «Привет!».
- **Deep link** на объект; состояние «прочитано» синхронизировано между каналами.
- **Настройки**: таблица тип × канал; «только важное» как пресет; отписка от всего в один шаг.
- **Email**: транзакционные с отдельного домена/адреса; маркетинг с List-Unsubscribe; тема = суть; preheader = следующий шаг.
- **Возврат по событию**: продукт генерирует реальные причины (новые люди, ответы, итоги) и сообщает только о них.
- **Измерять**: opt-in по платформам, отписки по классам, CTR по типам, отключения после отправки — антиметрика.

## Вопросы для брейншторма

1. В какой момент фичи человек сам захочет узнать «что дальше»? Там ли запрос разрешения?
2. Какие классы уведомлений создаёт фича и какие дефолты у каждого?
3. Какой канал выберет наш пользователь и предлагаем ли выбор?
4. Сколько уведомлений в неделю получит активный пользователь при худшем сценарии?
5. Как группируются события и есть ли лимит?
6. Что написано в уведомлении и куда оно ведёт?
7. Учитываем ли часовой пояс и тихие часы?
8. Как отписаться от одного типа и от всего?
9. Какая реальная причина вернуться возникает на 2-й, 7-й, 30-й день?
10. Какую антиметрику смотрим (отключения после отправки)?

## Признаки проблемы

Системный запрос на старте · один переключатель «уведомления» · акции в push вместе с ответами · «У вас новое событие» · ссылка на главную · 3 письма в неделю «что нового» · отправка в 3 часа ночи · бейдж на маркетинг · «Мы скучаем по вам».
